# 地震の再現動画 (R3)

地震のあと、記録 (jsonl) から当時の画面を描き直して動画にし、YouTube へ自動でアップロードする。
docs/quake-archive.md の 4 章 (R3) の続き。

## 1. 方針 (2026-09-30 決定、案 B)

- 描画は **native** (eq-server の中の Rust の描画) を使う。e2 では Chrome を使わない (メモリが足りない)。
- native に、地震波・緊急地震速報・のちに判明する震源・予想震度の札を足す。これで **ライブの YouTube 配信も同じ表示になる**。
- 再現動画は e2 の上で、記録から **nice 19 で、空き時間に** 描き直す。急がないので、リアルタイムでなくてよい。
- 音は eq-server の音の合成 (mixer) で入れる。揺れの始まりの音・2 秒ごとの刻み・警戒音 (web の R1.3 と同じ規則)。
- アップロードはキューにして、1 日に上げられる本数の範囲で順に上げる。
  - 近い震源で続いた地震は「連続地震」として 1 本にまとめ、チャプターを付ける。

## 2. 段階

| 段階 | 中身 | 確かめ方 |
|---|---|---|
| R3.1 | native に緊急地震速報と地震波を描く (ライブ配信で使う) | 記録の再生 (replay) で、手元のファイルに書き出して見る |
| R3.2 | 記録から描き直してファイルに書き出す (時計を記録の時刻で進める、音を入れる) | 茨城・与那国・能登で動画を作る |
| R3.3 | アップロードのキュー (連続地震のまとめ、チャプター、割り当て) | 非公開でのアップロードを 1 本 |

段階ごとに仕様を足し、リリースしてから次へ進む。

## 3. R3.1: native に緊急地震速報と地震波を描く

### 3.1 今の native

- 表示の判断は `crates/eq-server/src/broadcast/native/model.rs` にある (純粋な関数)。
  - web の priority.ts・groups.ts・scale.ts と同じ結果になるように作られている。
- 対象は地震情報 (Quake) だけ。緊急地震速報 (Eew) と地震波は描かない (docs/broadcast-native.md の「作らない」)。
- 地震の画面か平時かは `calm` (watch) で配信に伝わる。地震の画面では fps (10) で、平時は fps_calm (2) で描く。

### 3.2 足すもの (web と同じ見た目・同じ規則にそろえる)

web の該当する実装を読んで、同じ規則にする。web/src/waves.ts、quakes.ts (`waveSources`)、view.ts (緊急地震速報のバナー、予測の塗り)、detail.ts (`forecastTag`)、scene.ts、map.ts、alert.ts を見る。

1. **緊急地震速報**
   - 受けた緊急地震速報 (予報・警報) を、同じ地震 (event_id) の最新の報でまとめる。取り消し (`cancelled`) は消す。
   - 地震の画面にする (`calm` を false)。
     - 表示を続ける時間は web の `activeEews` と同じ規則にする。
     - 同じ地震の地震情報が届いたら、表示を地震情報に切り替える規則も web と同じにする。
   - 描くもの
     - 震源の ✕。
     - 地域・県の予測の塗り (破線または半透明。web の見た目に近いもので、native で描けるもの)。
     - 地域の予測が空のときは、✕ の近くに「予測最大震度N」の札。
     - 画面の見出し (パネル) に、緊急地震速報であることと予報か警報か、震源、予測最大震度。
       - 警報は目立つ色にする (web のバナーと同じ考え方)。
2. **地震波**
   - 起点は web の `waveSources` と同じにする。緊急地震速報があればその秒単位の発生時刻。無ければ地震情報の分単位の発生時刻。
   - 地表での P 波・S 波の半径は waves.ts と同じ式と速さ (VP 6.5km/s・VS 3.75km/s、深さを考える)。
   - 発生から `WAVE_MAX_SEC` (180 秒) で消す。
   - 同じ地震の緊急地震速報と地震情報で、波を二重に描かない。
   - 地図の投影 (native の geo.rs) で円を描く。
     - 半径は km から画面の座標に直す。緯度による歪みは、今の投影に合わせて扱う。
     - 楕円や多角形の近似でよい。
   - 波の間は、コマごとに描き直す (地震の画面の fps)。
3. **表示の判断を model.rs 側に置く** (純粋な関数、時刻は引数)。描く側 (draw.rs・panel.rs など) は判断しない。
4. 音は R3.2 で扱う。R3.1 では、今の音の知らせ (`notices`) の振る舞いを変えない。

### 3.3 やらないこと (R3.1)

- 震度の「のちに判明する震源」(再生だけの表示)。R3.2 で、記録から描き直すときに足す。
- 沖縄などの別枠の描き分けの見直し。今の native の枠の作りのまま描く。

### 3.4 テスト (cargo test)

- 緊急地震速報のまとめ: 最新の報、取り消し、表示を続ける時間、地震情報への切り替え。
- 地震波の起点の選び方と、P 波・S 波の半径 (深さあり)、180 秒で消えること。
- 予測最大震度の札を出す条件。
- 描画は、決まった入力で 1 コマ描いて、落ちないこと、画面の決まった場所の色が変わることくらいでよい。見た目の細部までは比べない。

### 3.5 確かめ方 (Mac。e2・YouTube には触らない)

- `tools/broadcast_load.py samples/scenarios/noto2024.jsonl --speed 1 --duration 150 --keep` で書き出し、ffmpeg で PNG を数枚切り出して見る。
  - 見る場面: 緊急地震速報 (警報) の直後、波が広がっている最中、地震情報に切り替わったあと。
  - `--keep` などで出力を残せないときは、手で立ててよい。
- 本番の `https://eq.fuga.jp/api/archive?from=1790744400000&to=1790745300000` (与那国、予報のみ) を、replay で読める形にして流す。形を変えるための一時的なスクリプトはコミットしない。
  - 予報の札と ✕ が出ること。
- 負荷 (`tools/broadcast_load.py`、noto2024 speed 4 の 100 秒、ffmpeg の経路、e2 と同じ encode) を、R3.1 の前と比べる。CPU とメモリが大きく増えないこと。数値を PR に書く。

### 3.6 実装で決めたこと (R3.1)

仕様から変えた点と、その理由。

- 判断の置き場所は `broadcast/native/eew.rs` (純粋な関数)。model.rs が 400 行に近いので、緊急地震速報と地震波の分は別ファイルにした。model.rs の `QuakeSummary` には地震波の起点のための `origin_ms` だけを足した。
- 細分区域 (地域) での塗りは描かない。web も、日本全体の表示では県の塗りだけで、地域の塗りは寄ったときだけ (map.ts の `applyView`)。native の枠は固定の全体表示なので、県の塗りだけにした。地域の予測があるかは、札を出すかの判断にだけ使う。
- 地震情報の上に、同じ地震の予測を残す塗り (`keepForecast`・`overlayForecast`) は描かない。地震情報が届いたら、web と同じ規則で地震情報に切り替える。
- 予測の塗りは、破線ではなく半透明の塗りと白い縁。web は点滅させるが、native は 1 秒ごとにしか塗りを描き直さない (負荷のため)。
- 地震波は文字と塗りの上に重ねる (web は文字の下)。文字と塗りは 1 秒ごとに描き、コマごとには波の円だけを重ねて I420 にする。これで 10fps でも eq-server の CPU は約 2 倍にとどまる。
- 地震の画面を続ける時間は、緊急地震速報は受けてから 3 分 (`activeEews`)。地震情報は今までどおり (最大震度で 1 分か 3 分) で、波がまだ続いていても伸ばさない (web の `calmState` は波が消えるまで伸ばす)。BGM の知らせの出し方は変えていない。
- 南西諸島の枠のすぐ外 (1.5 度以内) の震央は、枠の隅に寄せて ✕ と札を置く。与那国島の西の海 (北緯 23.6 度・東経 122.8 度) は本図にも枠にも入らず、そのままでは何も見えなかった。枠の作りは変えていない。

## 4. R3.2: 記録から音入りの動画を描き直す

### 4.1 決めたこと (2026-10-01、利用者の了承済み)

- **どこで作るか**
  - 作る道具は 1 つのコマンドにして、e2 (Linux x86_64) でも Mac (aarch64) でも同じに動くようにする。
  - **Mac は常時動いていることを前提にしない。** e2 だけで全部回ることを基本にする。Mac は、起きていれば手伝う役 (R3.3 で扱う)。
  - e2 では、負荷の低い時間に、CPU とメモリの上限を付けて作る。順番待ち (キュー) と時間の決め方は R3.3 で扱う。
    - R3.2 では、コマンドが自分で e2 の詰まりを見て、詰まっていれば待つところまで作る (4.3 の 7)。
  - e2 のメモリは 1GB で、zswap は効いているが余裕は少ない。2026-10-01 07:00 にメモリ不足でディスク待ちが詰まった。
- **コマの時刻**: 固定 fps でコマを埋めて ffmpeg に渡す。既定は 5fps、`--fps` で変えられる。
- **音**: 先に音だけを AAC にしてから、映像と合わせる (ffmpeg を 2 回)。生の音声の一時ファイル (15 分で約 160MB) は作らない。
- **1 本の中身**: 対象の地震の報だけに絞る。対象は、範囲の中で最大震度が一番大きい地震。連続地震のまとめは R3.3。
- **のちに判明する震源**: 始まりから、薄い ✕ と地震波を出す (web の R1.2 と同じ)。ライブの配信の振る舞いは変えない (引数で渡し、ライブは無し)。
- **何も届かない間**: 20 秒を超える間は早送りで詰めて、「早送り」を出す (web の R1.1 と同じ)。早送りの間は、刻みの音も始まりの音も鳴らさない。
- **再現の印**: 上のバーの右の label に「記録から再現」を出す。テスト配信の赤い帯は使わない。
- **天気・警報・BGM**: 出さない・流さない。平時の画面は、前後の数秒だけにする。
- **音の規則**: web の R1.3 と同じにする。
  - 揺れの始まりの音: 最大震度 3 以上でチャイム、未満でピンポン。
  - 2 秒ごとの刻み。
  - 報の警戒音: 緊急地震速報の最初の報と警報に上がったとき、地震情報の最初の報。
  - 訓練報は鳴らさない。3 秒以内に重なった音は、強いほう 1 回にまとめる。

### 4.2 コマンドの形

```
eq-server replay-video --from <ms> --to <ms> --out x.mp4
    [--events data/events.jsonl | --archive https://eq.fuga.jp]
    [--fps 5] [--no-zoom] [--label "記録から再現"] [--map-dir map] [--font ...] [--ffmpeg ffmpeg]
```

- 既定では、web と同じように震源へ寄る (docs/eew-hold-and-native-zoom.md)。`--no-zoom` で常に日本全体を映す。
- 寄るときは地図データに `areas.geojson` (地震情報細分区域) も読む。読めなければ警告を出し、県の範囲で寄る。

- `--events` は jsonl を直接読む (e2 で使う)。`--archive` は `/api/archive` から取る (Mac で使う)。どちらかは必須。
- `--from/--to` は報を集める範囲。動画の始まりと終わりは、そこから決める。
  - 始まり: web の `historyStart` と同じ。緊急地震速報の秒単位の発生時刻の 10 秒前。無ければ最初の報の 10 秒前。
  - 終わり: 最後の報のあと、地震の画面が平時に戻るまで。
- 出力は mp4 (`-movflags +faststart`)。映像は libx264 (`-threads 1`、veryfast、CRF 23)、音は AAC。

### 4.3 作るもの (下調べの結果。docs の下調べの報告を参照)

1. native の描画の体 (`render_loop` の中身) を同期の関数に切り出す。ライブも同じ関数を使う。
2. 仮の時計 t で回すループ。t までに届いた報 (`received_at_ms <= t`) だけを渡す。
3. のちに判明する震源の判断 (web の `hindsightOf` と同じ規則) を native の判断の側に足す。
4. 音の規則 (純粋な関数) と、`AudioMixer` を仮の時計で回して音を作る部分。
5. ffmpeg を 2 回起動する部分。
   - 音: PCM を標準入力 → AAC。
   - 映像: rawvideo を標準入力、音のファイルと合わせる。
   - `-re`・`-use_wallclock_as_timestamps`・`anullsrc` は使わない。
6. 記録の読み取り。archive.rs の読み取りを使い回す。
7. **e2 の詰まりへの配慮**
   - Linux では `/proc/pressure/{io,memory}` の full の 60 秒平均を、30 秒ごとに見る。
   - 20% を超えたら、コマの描画と ffmpeg への書き込みを止めて待つ。ffmpeg は書き込みが止まれば待つ。
   - 10 分以上待っても下がらなければ、作りかけを消して失敗で終わる (R3.3 のキューがやり直す)。
   - Mac では見ない。
8. 推奨の起動の仕方を README に書く。e2 では次の形 (配信が既に Nice=19 なので、nice だけでは配信と五分五分になる)。
   - `systemd-run --user --wait -p CPUQuota=10% -p CPUWeight=1 -p MemoryMax=200M -p MemorySwapMax=0 eq-server replay-video ...`

### 4.4 テスト

- 仮の時計での報の絞り込み、のちに判明する震源、始まりと終わりの時刻。
- 音の規則: 始まりの音・刻み・報の警戒音・3 秒のまとめ・早送り中は鳴らさない。
- ffmpeg の引数 (`-re` などが無いこと)。
- 詰まりの判定 (PSI の文から待つかどうか)。

### 4.5 確かめ方 (Mac。e2・YouTube には触らない)

- 本番の `https://eq.fuga.jp/api/archive` (読むだけ) から、次の 3 つを作る。
  - 2026-09-30 14:00 の与那国島近海 (緊急地震速報の予報あり)。
  - 2026-09-29 04:45 の茨城県南部 (緊急地震速報なし)。
  - 2026-10-01 10:32 の埼玉県南部。
- samples/scenarios/noto2024.jsonl から、能登の本震 (警報あり) も 1 本作る。jsonl の形の違いの扱いは担当が決める。
- ffprobe で長さ・映像・音が読めること。PNG を数枚切り出して、薄い ✕、地震波、震度の出方、「記録から再現」の印を見る。
- 音は、鳴った時刻と種類の一覧をログに出して確かめる。
- Mac で、15 分の動画を作るのにかかった時間と、CPU・最大メモリを書く。e2 での見積もりも添える。

### 4.6 実装で決めたこと (R3.2)

仕様から変えた点と、仕様に書かれていなかったことの決め。

- 置き場: コマンドは `broadcast/replay/` (筋書き plan.rs・音の規則 sound.rs・ffmpeg encode.rs・詰まり ../psi.rs・報の取得 source.rs)。native 側は、描く体を `native/step.rs` の `Stepper::step` に切り出し (ライブも同じ関数。出力は変えていない)、のちに判明する震源を `native/hindsight.rs` に置いた。
- **筋書きと描画を分けた**: コマごとの当時の時刻・届いた報の数・鳴らす音は、描かずに純粋な関数で先に決める (`plan::build`)。音を先に AAC にでき、映像はその筋書きのとおりに描く。
- `--events` は 2 つの形を読む。最初の報の行に `received_at_ms` があれば eq-server の sink の jsonl (archive.rs の `read_range` を使い回す)。無ければ samples/scenarios の形 (上流の JSON のまま) とみなし、発表時刻を届いた時刻にする (web の履歴の再生と同じ)。`read_range` は 500 件で切るので、上限に達したら警告を出す (R3.3a でファイルを直接読むときは 5 万件に広げた)。
- 対象の地震: 範囲の地震情報と緊急地震速報 (最新の報) を、最大震度の大きい順、同じなら先に起きた順で選び、同じ地震 (`same_quake`) の報だけを残す。震源の無い震度速報は発生時刻だけで同じ地震に入る。津波・地震感知情報は入れない。
- のちに判明する震源は、本物の震源が届くまで **平時の画面のまま** 薄い ✕ と波を出す (上部は [平時] のまま。web は「平時」にしない)。札「のちに判明する震源」は本図に震源があるときだけ付ける (南西諸島の枠の隅に寄せる与那国のようなときは ✕ だけ)。
- 時計の飛ばしは web の `skipRanges` と同じ (報の届いた時刻の間が 20 秒を超えたら、前の報の 5 秒後から次の報の 5 秒前まで)。「早送り」は飛んだコマから動画の 3 秒間、時計の枠の右上に出し、その間は刻みの音を鳴らさない。最後の報のあとの居残り (地震情報は 1〜3 分) は飛ばさず、平時に戻ってから 5 秒で終える。web の `makePlan` の、波の外の静かな間の圧縮はしない (仕様に無い)。
- 音は web の `alertLevel` をそのまま写した。仕様の一覧に無いが web にある「各地の震度」の案内音 (info) も鳴らす。訓練報・取り消し報は鳴らさない。重なりは web の `playAlert` と同じ: 同じコマで届いた報は一番強い 1 つ。3 秒以内に続く音は、前より強いときだけ鳴らす (強いほうが後から来れば、前の弱い音に続けて鳴る)。揺れの始まりの音の強さは、動画に入れる全部の報の最大震度で決める (チャイムは 3 以上)。刻みの音は web の `pipSlot` と同じで、波があり早送りでないとき、当時の時刻の 2 秒の枠が進むたび。音を鳴らす時刻はコマの時刻 (5fps で 0.2 秒) に丸まる。
- ffmpeg: 音は `.audio.m4a` を出力の隣に作り、終わったら (失敗しても) 消す。映像は `-g` を 2 秒、音は 96kbps の AAC。失敗したら作りかけの mp4 も消す。
- ライブの配信は変えていない: `Scene` の新しい 2 つの項目 (`hindsight`・`fast_forward`) はライブでは `None`・`false`。

## 5. R3.3: 自動で作って YouTube に上げる

### 5.1 決めたこと (2026-10-01、利用者の了承済み)

- **ライブの配信と本番が最優先。** 動画作りは、いつでも止めて捨ててよい後回しの仕事。
  - **地震の画面の間は、すぐ止める (kill)。** 凍結 (freeze) だと作りかけのメモリ (約 180MB) を抱えたままになる。地震のときこそ配信と本番にメモリを回したいので、kill して作りかけを消し、キューに戻す。
  - **平時に e2 が重くなったら、一時停止 (freeze)。** e2 の PSI (io・memory の full の 60 秒平均) が高い間、または YouTube の健全性が落ちている間は凍結し、落ち着いたら解凍して続きから作る。凍結が 10 分続いたら kill してキューに戻す。
  - **始めない条件**: 地震の画面の最中、最後の地震の画面から 30 分以内、e2 が詰まっているとき。
- 根拠: 2026-10-01 13:27 に e2 で CPUQuota=10% で作ったら、75 秒の動画に 80 秒かかり、その間 YouTube の健全性が一時 noData になった。
- **Mac は常時稼働を前提にしない。** e2 だけで全部回る。Mac は起きていれば先に引き取る (R3.3c)。
- 連続地震 (近い震源で続いた地震) は 1 本にまとめて、説明文にチャプターを付ける。呼び名は「連続地震」「連続して発生した地震」。「群発地震」は気象庁の用語なので使わない。
- アップロードは、1 日に上げられる本数の範囲で、キューから順に上げる。
  - 認証情報は e2 の pd2 と共有 (`~/.config/pd2/youtube-upload-token.json`)。読むだけで、書き戻さない。
  - 割り当ても pd2 と共有 (pd2 は 1 日 2 本)。

### 5.2 R3.3a: 検知・まとめ・キュー・作る係 (e2)

1. **配信の状態の知らせ** (eq-broadcast の native に足す)
   - 地震の画面か平時かを、小さな状態のファイルに書く。例: `$XDG_STATE_HOME/eq-broadcast/state.json` に `{"calm": bool, "since_ms": …, "updated_ms": …}`。
   - 切り替わったときと、10 秒ごとに書き直す (最後のコマの時刻 last_frame_ms も載せる。docs/broadcast-status.md)。書けなくても配信は止めない。
   - 作る係は、`updated_ms` が 2 分より古ければ「配信の状態がわからない」とみなし、慎重な側 (地震の画面と同じ扱い) に倒す。
2. **作る係** (`eq-server replay-worker`、systemd のユーザー単位で常駐)
   - **検知**: 記録 (jsonl) を見て、動画にする地震を見つける。
     - 対象の基準 (例: 最大震度 3 以上、または緊急地震速報の警報) は設定にする。既定は録画の `min_scale` と同じ 30 と警報。
   - **まとめ**: 近い震源 (例: 50km 以内) で、前の地震から 30 分以内に続いた地震を 1 つのまとまりにする。
     - 最後の地震から 60 分静かになったら、まとまりを閉じてキューに積む。
     - 1 本が長くなりすぎないよう、まとまりの長さに上限を付ける (例: 3 時間、以降は次のまとまり)。
     - 数字は設定にして、既定値を担当が決める。
   - **キュー**: `~/work/eq-replay/queue/` に、1 つのまとまりごとの JSON を置く。
     - 中身: 範囲・地震の一覧・状態 (待ち・作り中・できた・上げた・失敗)・やり直しの回数。
     - 人が見てもわかる形にする。
   - **作る**: 条件 (5.1) がそろったら、キューの古い順に 1 つ取り出す。
     - `systemd-run --user --unit=eq-replay-job-<id> -p CPUQuota=… -p CPUWeight=1 -p MemoryMax=200M -p MemorySwapMax=0 -p Nice=19 eq-server replay-video …` で作る。
     - まとまりが複数の地震なら、1 本の動画にする。
       - R3.2 の replay-video は 1 つの地震を対象にしている。複数の地震を続けて描き、地震と地震の間を早送りで詰める形に広げる。
       - 各地震の始まりの、動画の中の時刻を記録する (チャプターに使う)。
   - **見張り** (作っている間、数秒おき)
     - 配信の状態が地震の画面になった → `systemctl --user kill` (または stop) で止める。作りかけを消して「待ち」に戻す。
     - PSI が高い、または YouTube の健全性が bad・noData (5.1。API は作っている間だけ 1 分おきに見る) → `systemctl --user freeze`。
       - 落ち着いたら `thaw`。
       - 凍結が 10 分続いたら止めて「待ち」に戻す。
     - やり直しが 5 回を超えたら「失敗」にして、ログに残す。
   - できた動画は `~/work/eq-replay/done/` に置く。キューの状態を「できた」にする。
   - CPUQuota の既定は 5% (10% で配信に響いたため)。設定で変えられる。
3. **設定**: `[replay]` の節 (broadcast.toml とは別のファイルでもよい。担当が決める)。
   - 検知の基準、まとめの数字、PSI のしきい値、CPUQuota、置き場所。
4. **テスト**
   - 検知とまとめの判定 (純粋な関数)。
   - キューの状態の移り変わり。
   - 止める・凍結する判定: 配信の状態・PSI・健全性・時間 → 何をするか。
   - 状態のファイルが古いときの扱い。
5. **確かめ方 (Mac)**
   - 記録 (samples の能登、本番の `/api/archive` を読むだけ) から、検知とまとめが期待どおりになること。
     - 能登は、前震・本震を含む連続地震として 1 本になることを見る。
   - Mac では systemd が無いので、作る係の「止める・凍結する」は、判定の関数のテストと、手で状態のファイルを書き換えての確かめで代える。e2 での確かめはコーディネーターが行う。
6. 置き方 (deploy/) と README に、e2 での常駐の仕方 (`eq-replay-worker.service`) を書く。

### 5.2.1 実装で決めたこと (R3.3a)

仕様から変えた点と、仕様に書かれていなかったことの決め。

- 置き場: 作る係は `broadcast/replay/worker/` (検知 detect.rs・キュー queue.rs・止める判断 decide.rs・健全性 health.rs・単位の引数 job.rs・設定 config.rs・試し scan.rs)。状態のファイルは配信側の `broadcast/calm_state.rs` (書く側と読む側の判断を 1 か所に置く)。設定は `broadcast.toml` とは別の `replay.toml` の `[replay]` の節 (`deploy/replay.e2.toml`)。
- 状態のファイル: 最初の画面が描けるまで書かない (calm の初期値は仮の値で、データを受ける前に「平時」と書かないため)。`since_ms` は今の状態になった時刻で、配信を始めたときも更新する。このため、eq-broadcast を再起動すると、作る係は「最後の地震の画面から 30 分」の数え直しになる (慎重な側)。chrome の配信は書かないので、作る係は動かない (native の配信が前提)。
- 検知の対象: 同じ地震の地震情報と緊急地震速報を 1 つにまとめ、震度は地震情報があればその観測、無ければ緊急地震速報の予測 (予測 4 でも観測 3 なら 3)。警報は震度にかかわらず対象 (`warning = false` で外せる)。訓練報と、最新の報が取り消しの緊急地震速報は数えない。
- まとめの数え方: 前の地震 (まとまりの最後の地震) から 50km 以内・30 分以内なら続く。震源が分からない地震は時間だけで決める。最初の地震から 3 時間を超える地震は次のまとまりにし、そのとき前のまとまりは静かになるのを待たずに閉じる。まとまりの閉じ方は「最後の報が届いてから 60 分」。
- キューへの積み方: 記録の最近 6 時間 (`lookback_hours`。max_group_hours + quiet_min より長くする) を 5 分ごとに読み直し、閉じたまとまりのうちキューに無いものを積む。「キューにある」は、まとまりの地震のどれかが、キューの地震と同じ地震 (`same_quake`) かで決める (見る範囲の端でまとまりが欠けて見えても、二重に積まない)。
- 作る範囲: 最初の地震の発生の 2 分前から、最後の報の 10 分後まで。
- 複数の地震を 1 本にする (replay-video): `--quake <発生時刻>[,<緯度>,<経度>]` を地震の数だけ渡す。時計は 1 本で、地震と地震の間は早送りで詰める。2 つ目以降の地震は、始まり (緊急地震速報の発生の 10 秒前、無ければ最初の報の 10 秒前) に「報が届いた」とみなして時計の飛ばし先を決める。飛んだ先でその地震の薄い ✕ と揺れの始まりの音が出る。薄い ✕ と波は、始まっている地震のうちいちばん新しく起きたもの 1 つだけを出す (ライブの `Input` は変えない。発生が 180 秒以内に重なる連続地震では、古い方の波が消える)。揺れの始まりの音と、地震情報の最初の報の警戒音は、地震ごとに数える。各地震の始まりの動画の中の時刻は `--chapters` で JSON に書き、作る係がキューの JSON の `chapters` に写す。動画の長さの上限は 1 時間から 3 時間にした。
- 記録の読み取り: `/api/archive` は今までどおり 500 件で切るが、ファイルを直接読むときは 5 万件まで読む (3 時間の連続地震が 500 件を超えて、終わりの報が欠けるため)。
- 作る単位: `systemd-run --user --wait --collect --quiet --unit=eq-replay-job-<id>-<秒>` (やり直しのたびに名前を変える)。`WorkingDirectory` は作る係と同じにして、`map_dir` などの相対パスがそのまま通るようにした。作る係が落ちたら、次に始まるときに `eq-replay-job-*` を stop し、作り中のまま残った印を待ちに戻し、`work/` を空にする。
- 止める: `systemctl --user kill --signal=SIGKILL` (凍結している単位でも確実に止まる。SIGTERM は凍結中は解凍するまで届かない)。30 秒たっても終わらなければ `stop`。凍結・解凍の命令が失敗したときは、その作りかけを止めて失敗に数える。
- やり直しの数え方: 失敗 (replay-video の失敗・凍結の命令の失敗) と、凍結が 10 分続いて止めたものは数え、失敗のあと 10 分は作り直さない。地震の画面で止めたものと、作る係を止めたときのものは数えない (地震は予測できず、動画の出来のせいではないため)。6 回目の失敗で `failed`。
- 健全性: Rust で書いた (`liveStreams.list` だけ。1 回 1 単位)。受け口が受信中でない、または受信中でも健全性が bad・noData のときだけ「落ちている」。名前に合う受け口が無い・読めないときは「わからない」で、止める理由にしない。仕様の「始めない条件」には健全性が無いが、始める前にも 1 回見る (落ちているのに始めて、すぐ凍結するのを避けるため)。
- Mac での確かめ: `systemd-run`・`systemctl` のコマンド名を設定 (`systemd_run`・`systemctl`) で差し替えられる。Mac では pid に signal を送る代わりのスクリプトで、検知 → 積む → 作る → 地震の画面で止める → 平時が続いて作り直す、を確かめた。凍結・解凍の命令と、systemd の単位の制限は Linux (e2) でしか確かめられない。

### 5.3 R3.3b: アップロード (v0.28.0 で、Mac の作る係に入れる)

6 章のとおり、動画は Mac だけで作る。このため、アップロードも Mac の作る係がやる (e2 の認証情報の共有はやめた)。
当初の案 (e2 の pd2 の認証情報を読むだけにする・`done/` の mp4 を 7 日で消す) は取り下げた。

- 「できた」の動画を、キューの古い順に YouTube Data API v3 の `videos.insert` (resumable upload) で 1 本ずつ上げる。作っている間は上げない (作るのと上げるのは同時にやらない)。
- 認証は OAuth 2.0 の installed app (ループバックのリダイレクト・PKCE)。範囲は `youtube.upload` だけ。一度だけ人が `eq-server youtube-auth` を実行する (6.8)。
- タイトル・説明文
  - 1 つ: 「【地震の記録】2026/10/02 17:39 熊本県熊本地方 最大震度3 (再現)」。
  - 連続地震: 「【連続して発生した地震の記録】2026/09/30 14:00 与那国島近海ほか計 5 回 最大震度5弱 (再現)」。
  - 説明文: 当時の記録から再現した映像であるという断り書き、地震の一覧 (時刻・震源・M・深さ・最大震度)、出典 (画面の出典と同じ)。連続地震で、チャプターが条件を満たすときは、先頭にチャプターを置く。条件は、先頭が 0:00・3 個以上・各 10 秒以上で、満たさないときは付けない (YouTube は条件を満たさないとチャプターとして扱わない)。
- 公開範囲は設定 (`youtube_privacy`) で、**既定は非公開 (private)**。公開・限定公開への変更は、利用者が出来を見て YouTube Studio で手でやる。カテゴリは 25 (ニュースと政治)。
- 割り当て
  - 1 日の本数の上限を設定 (`youtube_daily_limit`、既定 3) にする。ローカルの状態ファイルで数え、太平洋時間 (夏時間を考える) の 0 時で区切る (YouTube の割り当てが太平洋時間の 0 時に戻るため)。
  - `quotaExceeded`・`uploadLimitExceeded` などが返ったら、その太平洋時間の日はもう上げない。
  - 5xx・ネットワークの失敗は、間を空けて (1 分から倍々、最大 30 分) 全体をやり直す。警告は切れたときの 1 回だけ。
  - 4xx で断られたものは、5 回までやり直して、超えたら諦める (キューの `error` に残す)。
- 認証情報の更新: `invalid_grant` (取り消し・期限切れ) が返ったら、明確なエラーを 1 回出して上げるのをやめる。`youtube-auth` をやり直してトークンのファイルが書き換わると、自動で再開する。
- 上げた動画の ID と時刻を、キューの JSON (`youtube_id`・`uploaded_ms`) に残し、状態を `uploaded` にする。二重には上げない。`done/` の mp4 は消さない (`youtube_delete_after_upload = true` で消せる)。
- トークンは、アクセストークンとその期限を、トークンのファイル (モード 0600) に書き戻す。ログには、トークン・クライアントの秘密・Authorization ヘッダーを出さない。
- Google との通信は trait の後ろに置き、テストでは偽物を使う。本物の Google には、テストから触らない。

### 5.4 R3.3c: Mac の手伝い (R3.3b のあと、任意)

- Mac が起きていれば、e2 のキューの「待ち」を引き取って (ssh で印を付ける)、Mac で作る (`--archive`)。できた mp4 は e2 の `done/` に送る。アップロードは e2 が行う。
- Mac が途中で寝たら、印の期限 (例: 30 分) が切れて、e2 が引き取り直す。

### 5.5 R3.3a の手直し: e2 で作るときに配信に響かないように (v0.22.1)

2026-10-01 15:35〜15:54 に、e2 で与那国 (09/30 14:00) を作らせた結果。

- CPUQuota 5% で作り始めて 8 分後、io の PSI が 20% を超えて凍結した。
- 凍結の間にディスク待ちは下がったが、YouTube の受け口の健全性が bad になり、10 分で止めた。動画はできなかった。
- 見当
  - 再現の映像の ffmpeg が約 130MB (先読みあり) で、e2 のメモリを圧迫した。キャッシュの追い出し → ディスク待ちが増え、配信に響いた。配信の ffmpeg は `-tune zerolatency` で 50〜80MB。
  - **凍結は CPU とディスクを手放すが、メモリは抱えたまま。** 配信を助けきれない。

直すこと:

1. **再現の圧縮を軽くする**
   - 映像の ffmpeg に `-tune zerolatency` を付ける (先読みをしない)。`-rc-lookahead 0` などで同じ効果を得られるなら、それでもよい。
   - 最大メモリを測り、前後の数値を PR に書く。目安は ffmpeg 60MB 以下、eq-server と合わせて 120MB 以下。
   - 画質と大きさの前後も書く (同じ CRF で、ファイルの大きさが大きく増えないこと)。
2. **重くなったら、凍結より止める (kill) を先にする**
   - e2 の PSI の超過、または YouTube の健全性の低下を見たら、すぐ止める。作りかけを消して、待ちに戻す (やり直しの回数に数える)。
   - 凍結は使わない。設定で凍結に戻せるようにしておく (`on_busy = "kill" | "freeze"`、既定は kill)。
   - 止めたあとは、`retry_wait_min` (既定 10 分) を空けてから作り直す。
3. **作る時間帯を限る**
   - 設定 `hours` (日本時間。この時間の中でだけ作り始める)。既定は `"10-15,21:30-23"` (日中と夜の早い時間)。
   - 時間帯の終わりで作りかけなら、終わりまで作る (途中で止めない)。ただし 2 の条件では止める。
4. **作る前の確かめを強める**
   - 始める前に、e2 のメモリの空き (`/proc/meminfo` の MemAvailable) が一定以上 (既定 250MB) であることを条件に足す。
5. テスト: 時間帯の判定、止める判定 (PSI・健全性・メモリの空き)、ffmpeg の引数 (`zerolatency`)。
6. 確かめ方 (Mac)
   - 与那国と能登を作り直し、メモリ・時間・ファイルの大きさを前後で比べる。
   - e2 での確かめは、コーディネーターが夜の時間帯に行う。

### 5.5.1 実装で決めたこと (v0.22.1)

- 圧縮: `-tune zerolatency` だけで足りた (先読み・B フレーム・mbtree をやめる)。`-threads 1` と CRF 23・veryfast は変えない。ライブの配信 (broadcast/ffmpeg.rs) は触っていない。
- 測った結果 (Mac aarch64、`/usr/bin/time -l` と ps の 0.5 秒ごとの標本。ffmpeg の最大メモリ / eq-server の最大メモリ / 作った時間 / mp4 の大きさ)
  - 与那国 (09/30 14:00、動画 323 秒): 前 134MB / 60MB / 9 秒 / 8.3MB → 後 71MB / 56MB / 7 秒 / 9.9MB
  - 能登 (samples、動画 489 秒): 前 135MB / 59MB / 8 秒 / 17.7MB → 後 78MB / 59MB / 7 秒 / 22.5MB
  - ffmpeg は約 45% 減ったが、目安の 60MB 以下には Mac では届かない (ffmpeg を起動しただけで Mac では約 26MB、エンコーダで約 40MB が基準になる。Linux の glibc では小さいはずで、e2 で測り直す)。eq-server は描画の分で約 57MB のまま。ファイルは同じ CRF で 18〜27% 大きくなる (先読みと B フレームが無いため)。
- 重くなったとき (`on_busy`): 既定は `kill`。PSI の超過・YouTube の健全性が bad のどちらかで、すぐ `kill --signal=SIGKILL` し、作りかけを消して待ちに戻す。**やり直しに数える** (失敗と同じで、`retry_wait_min` を空けて、5 回を超えたら `failed`)。`freeze` にすると 5.2 の動き (凍結・解凍・10 分で止める) に戻る。
- 時間帯 (`hours = "1-5"`): 日本時間で 1:00 以上 5:00 未満に作り始める。`"22-5"` のように始めが大きければ日をまたぐ。`"0-24"` で一日中。`"10-15,21:30-23"` のようにカンマで複数書け、分も書ける (e2 は夜中 1〜2 時半ごろポッドキャストの作業で重いので、日中と夜の早い時間にしている)。始めるときだけ見るので、作りかけは過ぎても続ける。
- メモリの空き (`min_mem_mb = 250`): 始める条件にだけ足した (`/proc/meminfo` の MemAvailable。読めない Mac では見ない)。作っている間は見ない (仕様どおり、止める条件は PSI と健全性)。

## 6. Mac で作る (v0.25.0)

### 6.1 決めたこと (2026-10-04、利用者の了承済み)

- 再現動画は **Mac だけで作る**。e2 は弱く、10fps の描画に 1.5〜2 コア要るため、作ると配信が落ちた。e2 では作る係を動かさない (`eq-replay-worker.service` は使わない)。
- Mac は常時起きているわけではない。起きているあいだに、取りこぼした地震をまとめて作る。止まっている間に起きた地震は、起きたあとに記録から見つけるので失われない。
- 作る係は 5 章のものをそのまま使い、設定で Mac 向けにする。

### 6.2 設定

- `runner = "systemd" | "inline"` (既定 `systemd`)。`inline` は `systemd-run` を使わず、`replay-video` を子プロセスとして直接起動する。CPUQuota・MemoryMax は付けない。引数は `systemd` のときと同じ。作る係が止まるとき・止めるときは、子を kill する。
- `gate = "vm" | "none"` (既定 `vm`)。`none` は、配信の状態のファイル・PSI・メモリの空き・YouTube の健全性の確認と、作っている間の「重いから止める」をやめる。`hours` だけは効く (Mac は `"0-24"`)。`/proc` は読まない。
- `events` に `http://` か `https://` の URL (例: `https://eq.fuga.jp`) を書くと、`/api/archive` から取る。サーバは 1 回に 1 時間まで (`from`〜`to` の差が 3,600,000 ミリ秒以内、1 回 500 件まで) なので、1 時間ずつに分けて取り、`id` が同じ報を 1 つにして検知に渡す。作るときも同じ URL から取る (`replay-video --archive`)。1 本が 1 時間を超えるときは、`replay-video` が 1 時間ずつ取って 1 つにする。
- **止まっていた間を取り戻す (checkpoint)。** URL のときは、前に見終えた時刻を `dir/checkpoint.json` (`{"scanned_until_ms": …}`) に残す。次の見直しは、`max(checkpoint - overlap, 今 - catchup_max_hours)` から今までを 1 時間ずつ取る。`overlap` は `max_group_hours + quiet_min` (checkpoint の時点で開いていたまとまりの始まりを含めるため)。checkpoint が無い最初は、`lookback_hours` だけさかのぼる。checkpoint は、**全部取れて、キューに積めたときだけ**今に進める。途中で 1 つでも失敗したら動かさず、次の `scan_secs` で同じところからやり直す。同じまとまりを二重に積まないのは 5.2.1 のとおり (キューにある地震と照らす)。
- `catchup_max_hours` (既定 24、Mac の例は 168 = 7 日。`lookback_hours` 以上)。サーバのコード (`archive.rs`・jsonl の sink) には記録を消す仕組みが無く、`/api/archive` は jsonl を頭から読む。つまり、保管の長さは運用 (ファイルを残している間) で決まる。これより古い地震は、止まっていても動画にしない。
- **取る先への負担を抑える。** 範囲と範囲の間に 1 秒空ける (eq.fuga.jp は 1GB の VM で、1 回ごとに記録を頭から読む)。7 日さかのぼっても約 3 分で、定常では (4 時間 + 経過分) の数回だけ。取れなくなったら (オフライン・スリープ明け)、その回は何もせず、警告は切れたときの 1 回だけ出して、続く間は静かに次の `scan_secs` を待つ。戻ったら 1 回だけ知らせる。
- `inline_wrap` (既定は空): `inline` のとき、子の前に付けるコマンド。Mac は `["/usr/sbin/taskpolicy", "-b"]`。macOS の background の優先度 (CPU・ディスク・ネットワークが後回し) で動かし、子の ffmpeg も引き継ぐ。普段の作業を優先し、遅くなってよい。作るのは 1 本ずつ。
- `runner = "inline"` と `on_busy = "freeze"` の組み合わせは、凍結に systemd が要るので設定の読み込みで断る (`gate = "none"` なら凍結は使わないので構わない)。
- 例: `deploy/replay.mac.toml`。YouTube への投稿は 6.8。

### 6.3 置き方 (Mac)

リリースの tar.gz (aarch64-apple-darwin) を `~/work/eq-replay/release/` に展開する。地図の素材 (`japan.geojson`・`neighbors.geojson`・`warning-areas.geojson`・`areas.geojson`・`stations.json`) は、その中の `web/dist` をそのまま `map_dir` にする。コピーや symlink は要らない。バージョンを上げるときは、展開し直して `launchctl kickstart -k` で作る係を入れ直す。

```sh
mkdir -p ~/work/eq-replay/release
tar xzf eq-server-<version>-aarch64-apple-darwin.tar.gz --strip-components=1 -C ~/work/eq-replay/release
xattr -dr com.apple.quarantine ~/work/eq-replay/release
brew install ffmpeg
cp deploy/replay.mac.toml ~/work/eq-replay/replay.toml
sed "s|/Users/USERNAME|$HOME|g" deploy/jp.fuga.eq-replay-worker.plist > ~/Library/LaunchAgents/jp.fuga.eq-replay-worker.plist
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/jp.fuga.eq-replay-worker.plist
```

止めるときは `launchctl bootout gui/$(id -u)/jp.fuga.eq-replay-worker`。ログは `~/work/eq-replay/worker.log`。launchd は PATH が短いので、plist で `/opt/homebrew/bin` を足してある (ffmpeg のため)。

### 6.4 スリープと途中停止

- 作っている最中にスリープすると、`replay-video` も一緒に止まり、起きたら続きから進む。壁時計の時刻は変わらないが、動画の中の時刻は記録から決まるので、できあがりに影響しない。
- 作る係や子が途中で kill されたり失敗したりしても、`work/` の作りかけは `done/` に移さない。できた動画として数えるのは、子が成功で終わり、`done/` への移動に成功したときだけ。止まったものは 5.2.1 のやり直しの規則に従って待ちに戻る。
- 作る係が落ちて再起動したときは、`work/` を空にして、作り中のまま残った印を待ちに戻す。

### 6.8 YouTube への投稿 (v0.28.0、R3.3b)

できた動画は、作る係が自動で YouTube に上げる。方針は 5.3。ここは Mac での使い方と決めたこと。

**初回に一度だけ (人がやる)**

1. Google Cloud で YouTube Data API v3 を有効にし、OAuth クライアント (種類は「デスクトップアプリ」) を作って、JSON を `~/.config/eq-replay/youtube-client.json` に置く (`{"installed": {...}}` の形)。同意画面が「テスト」のままなら、自分のアカウントをテストユーザーに入れる。なお、テストのままだと、リフレッシュトークンは 7 日で切れる。続けて使うなら、同意画面を「本番」にする (範囲は `youtube.upload` だけなので、確認の手続きは要らないが、「未確認のアプリ」の警告は出る)。
2. 次を実行する。表示された URL をブラウザで開き (macOS では自動で開く)、許可する。

```sh
~/work/eq-replay/release/eq-server youtube-auth \
  --client ~/.config/eq-replay/youtube-client.json \
  --token ~/.config/eq-replay/youtube-token.json
```

3. `~/.config/eq-replay/youtube-token.json` ができる (モード 0600。リフレッシュトークンと、アクセストークンの控え)。作る係は、次の見直しで自動で使い始める。入れ直しは要らない (`replay.toml` を書き換えたときだけ、`launchctl kickstart -k` で入れ直す)。

**置き場所**

| ファイル | 中身 |
|---|---|
| `~/.config/eq-replay/youtube-client.json` | OAuth クライアント (人が置く。読むだけ) |
| `~/.config/eq-replay/youtube-token.json` | `youtube-auth` が書く。作る係がアクセストークンの控えを書き戻す |
| `~/work/eq-replay/youtube-state.json` | 今日 (太平洋時間) に上げた本数と、割り当てを使い切ったか |
| `~/work/eq-replay/queue/<id>.json` | 上げた動画の ID (`youtube_id`)・時刻 (`uploaded_ms`)。状態は `uploaded` |

**動き**

- 公開範囲は既定で非公開 (`youtube_privacy = "private"`)。公開・限定公開にしたいときは、YouTube Studio で動画を開いて、公開範囲を手で変える。設定で `unlisted`・`public` にすることもできるが、出来を見てからにする。
- 1 日の本数は `youtube_daily_limit` (既定 3)。太平洋時間 (夏時間を考える) の 0 時で区切って数える。日本時間では夏は 16 時、冬は 17 時に切り替わる。`quotaExceeded`・`uploadLimitExceeded` が返ったら、その日はやめる。
- 通信が失敗したら、1 分・2 分・4 分…(最大 30 分) と間を空けて、最初から上げ直す (途中からの再開はしない)。警告は切れたときの 1 回だけで、続く間は静か。
- 4xx で断られたら、5 回まで数えて諦める。キューの `error` に理由が残る (mp4 は `done/` に残る)。
- `invalid_grant` (許可の取り消し・期限切れ) になったら、ログ (`~/work/eq-replay/worker.log`) に `youtube-auth をやり直してください` と出して、上げるのをやめる。もう一度 `youtube-auth` を実行してトークンのファイルが書き換わると、自動で再開する。
- トークンのファイルが無いあいだは、ログに「youtube-auth を実行してください」と 1 回だけ出して、上げない (動画は作り続ける)。
- 上げるのは、動画を作っていないときだけ。1 本ずつで、`taskpolicy -b` は子の作る処理にだけ付いている (上げるのは通信が主で、軽い)。
- `youtube_upload_token = ""` にすると、上げない。

**テスト**: Google との通信は `youtube::api::Api` の後ろにあり、テストは偽物で、タイトルと説明文・チャプターの条件・太平洋時間の日付 (日付変更線と夏時間)・1 日の上限・割り当ての超過・二重に上げないこと・トークンの更新 (成功・`invalid_grant`・401)・PKCE・リダイレクトの読み取り・トークンのファイルのモード 0600 を確かめている。本物の Google には、テストから触らない。

**意図的に空けている箇所**: 本物の HTTP (`youtube::api::Google`) と、同意の手続きの一連の動き (ブラウザ・実際の Google)。壊れても、最初の 1 本のときに表面化する。応答の判断は別の関数に分けてあり、そちらはテストしている。

## 7. 読み上げを入れる (v0.30.0)

ライブ (eq.fuga.jp) には Google の音声読み上げ (docs/tts.md) が入った。再現動画にも、同じ読み上げを足す。

### 7.1 決めたこと

- 動画を作る側は Google を呼ばない。サーバの `POST /api/tts/announce` (履歴の再生・デモ用。キャッシュ済みの部品だけで組み立て、合成はしない) から WAV をもらう。
- `replay-video --voice <サーバの URL>` で入れる。省けば読み上げなし (今まで通り)。作る係は設定の `voice_server` を渡し、空なら省く。Mac の設定 (deploy/replay.mac.toml) は `https://eq.fuga.jp` にする。
- どの報を読むかは、ブラウザ・配信と同じ規則にする。警戒音を鳴らす報 (`alert_level`) と、警戒音は鳴らさないが読む津波予報 (`should_read_without_alert`)。
- 本文はブラウザの履歴の再生と同じ形にする。報は `source` を `demo`、id を `…#demo1` にし (緊急地震速報は event_id も)、`priors` には同じ地震・同じまとまりの、その報より前の報を最大 300 件、届いた順に付ける。
- 声は、その報の警戒音のあと (警戒音の長さだけ後) に始める。声は 1 本ずつ鳴らし、待ちは 4 本まで (あふれたら古いものを捨てる)。これは配信の mixer と同じ仕組み (`AudioMixer::push_voice`) をそのまま使う。動画には BGM が無いので、音を下げる (ダッキング) 相手はいない。
- WAV は 44.1kHz のモノラルで、mixer の周波数と同じなので、`rate` は付けず、変換もしない。
- サーバは小さな VM なので、要求は 1 本ずつ、300ms あけて送る。読む報の分だけで、ほかは送らない。
- 404 (読むものがない・キャッシュに無い) は普通のことで、その報は無音にする。通信できない・サーバが 404 以外のエラーを返したときは、警告を 1 回出して、残りの読み上げはやめ、読み上げなしの部分も含めて動画は作る。オフラインでも `replay-video` は動く。

### 7.2 テスト

偽のサーバ役を使い、次を確かめる。どの報に要求が出るか (警戒音の報・津波の初報だけで、続報・訓練・取り消しには出さない)、本文の形 (`source`・`#demoN`・priors の順と上限)、声が警戒音のあとに置かれて待ち行列に積まれること、404 は無音、通信の失敗では声なしで残りが作れること、`--voice` と `voice_server` の読み取り。
