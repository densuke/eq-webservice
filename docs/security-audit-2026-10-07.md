# セキュリティ監査（2026-10-07）

対象は eq-webservice v0.44.0、コミット `e3d4153`。Rust の HTTP・WebSocket・音声 API、外部情報の取り込み、通知プラグイン、YouTube 認証、フロントエンドの表示処理、デプロイ例、依存関係を確認した。

優先して対処したい問題は **高1件、中4件**。公開音声 API のメモリ消費が最優先で、その後に WebSocket と履歴 API の可用性対策を進める。TTS・Webhook に関する問題は、それぞれの機能を有効にした場合に影響する。既定設定では TTS と Webhook は無効。

実際の公開サーバーへの負荷試験は行っていない。再現は一時ディレクトリにコピーしたコードと偽の音声合成器、ループバックの HTTP サーバーで行った。本番設定・プロキシ・OS の実際の制限は未確認であり、公開範囲や影響の大きさは実環境で確認する必要がある。アプリケーションの実装は変更していない。

## S-01：公開音声 API の出力増幅

根拠：`crates/eq-server/src/tts/http.rs:109`、`tts/phrase.rs:94`、`tts/cache.rs:125`、`tts/wav.rs:88`。

`POST /api/tts/announce` は履歴・デモ再生用の公開 API。本文1MiBと先行報300件の制限はあるが、イベント内の `areas` の件数・重複、生成部品数、音声の総サンプル数に制限がない。津波警報・大津波警報では地域を全件読み上げるため、同じ地域を繰り返すだけで同じキャッシュ音声が何度も読み込まれる。

`announce_cached` は全ての PCM を保持し、`wav::join` と `wav::encode` でさらに連結用・出力用のバッファを作る。入力の1MiB制限は、このメモリ消費を制限しない。匿名の利用者が少数のリクエストでプロセスのメモリ上限を超え、地震情報の配信まで停止させる可能性がある。先行報と対象報に多数の地域を入れた場合には、差分計算にも地域間の反復比較が発生する。

**再現済み**：1秒の偽音声を「伊勢・三河湾。」のキャッシュに置き、その地域を128回含む津波警報を送った。Authorization なしで HTTP 200、入力 **13,470 bytes** に対して出力 **12,969,854 bytes（約963倍）**。実際の Google API は呼んでいない。プロセスを停止させる大きさまでの実験は行っていない。

修正案：イベントごとに地域数・文字列長・地域名の重複を検証する。生成部品数と総サンプル数に上限を設け、全バッファを確保する前に拒否する。音声 API 専用の同時実行数制限とリクエスト頻度制限を加える。音声部品の重複読み込みを減らすだけでは、巨大な連結出力を防げない。

## S-02：WebSocket の接続枠占有

根拠：`crates/eq-server/src/http.rs:52`、`:99`、`:112`、`:149`、`deploy/Caddyfile.example:6`。

500接続の上限はサーバー全体で共通で、利用者・IP ごとの制限はない。一人が500接続を維持すると、ほかの利用者の接続は503になる。定期 ping は送信しているが、pong の期限や送信のタイムアウトは設けていない。TCP 接続が生きているだけのクライアントを整理できず、接続枠を長く保持できる。

**部分的に再現済み**：異なるサイトの `Origin: https://unrelated.example` を付けた接続が HTTP 101 で受理された。500接続による枠の占有は実装から確認したもので、大量接続試験は行っていない。

この API は公開情報を送るものなので、異なる Origin を受け付けること自体を秘密情報の窃取とは評価していない。ただし、別サイトの閲覧者を接続枠の消費に使える経路になる。Origin 制限だけでは、Origin を偽装できる非ブラウザーのクライアントを防げない。

修正案：信頼するプロキシから取得した接続元 IP ごとに同時接続数と接続頻度を制限する。pong の期限、送信期限も設ける。ブラウザーの利用範囲に合わせて Origin を検証する。プロキシを使う場合、任意の `X-Forwarded-For` を無条件に信用しない。

## S-03：履歴 API の全記録走査

根拠：`crates/eq-server/src/archive.rs:54`、`:77`、`:87`、`:100`、`plugins/jsonl.rs:31`。

`GET /api/archive` は検索範囲を1時間、応答を500件、同時読み込みを2件に制限する。しかし実際の処理は、全ファイルの全行を JSON として解析してから、該当する全件を保持・ソートし、最後に500件へ切り詰める。空の検索結果を返す場合でも全ファイルを走査する。JSONL sink 自体にもローテーションはない。

匿名の利用者が2本の検索を繰り返すだけで、記録量に比例したディスク読み込みと CPU 消費を継続でき、ほかの履歴利用者は503になる。範囲内に多数の報がある場合は、500件制限を超えたメモリも一時的に保持する。同じマシン上のライブ配信に影響する可能性がある。

**静的確認**。既存テストは応答件数の制限を確認しているが、走査量や保持件数の上限を確認していない。実際の記録容量・本番での遅延は未測定。

修正案：日付単位の記録と時刻索引で検索対象を絞る。処理中の保持件数も制限し、範囲・ファイルの走査量と処理時間に上限を設ける。履歴 API の頻度制限・キャッシュを追加する。単純に500件で読み込みを止める場合は、ファイルの時刻順序が保証されるかを先に確認する。

## S-04：音声合成の予算確認と消費の競合

根拠：`crates/eq-server/src/tts/cache.rs:80`、`tts/budget.rs:54`、`:63`。

予算は合成前の `check` と、非同期の合成完了後の `record` に分かれている。異なる部品の合成は別々のロックで動くため、複数の処理が同じ残額を見て全て通過する。月間予算は課金の厳密な上限になっていない。

**再現済み**：上限3文字のキャッシュに、異なる3文字の文を同時に合成させた。両方が成功し、使用量は **6文字** になった。匿名の GET はサーバーが受信済みのイベントに対象を限定するが、キャッシュミス時には合成を行う。認証付きの独自文、公開イベントの合成、事前合成の間でも競合しうる。

修正案：合成前に使用済み文字数と予約中の文字数を同じロックで確認し、予約する。失敗時の予約返却と成功時の確定を実装する。異なる部品も含めた合成全体の並行数を制限する。タイムアウト後に続く合成も予約・同時実行数に含める。

## S-05：Webhook の独自認証ヘッダーの転送

根拠：`crates/eq-server/src/plugins/webhook.rs:27`、`:34`、`net.rs:14`。ロックされた `reqwest 0.12.28` の `src/redirect.rs:239` も確認した。

Webhook は設定された全ヘッダーを付け、reqwest の既定のリダイレクト追従を使う。reqwest は別 host・port への転送で Authorization や Cookie を取り除くが、`X-Api-Key` などの独自ヘッダーは取り除かない。送り先の転送設定ミス、オープンリダイレクト、送り先の侵害によって、設定した秘密が別の送り先へ送られる。

**再現済み**：ループバックに2つの HTTP サーバーを作り、一方の POST を302で別 port に転送した。`X-Api-Key: audit-placeholder` が転送先に届いた。実際の秘密情報は使っていない。公開 API から任意の送り先を指定できるわけではなく、Webhook を有効にして独自ヘッダーを設定した場合の問題。

修正案：Webhook 専用クライアントでリダイレクトを無効にする。転送が必要なら、HTTPS と許可した origin の範囲だけに限定し、秘密を付けたリクエストの転送を明示的に管理する。

## 確認できた防御と監査結果

- CSP、`nosniff`、フレーム制限、Referrer-Policy が HTTP ルーターに設定されている。
- 上流由来の名前・本文・属性値は主要な HTML 表示箇所でエスケープされ、バナー本文は `textContent` で表示される。津波等級は Rust の列挙型から出力される。今回確認した経路では、成立する XSS は見つからなかった。
- HTTP の外部応答は共通ヘルパーで8MiB、上流 WebSocket は1MiBに制限される。HTTP の取得にはタイムアウトもある。ただし一部の個別クライアントはこの共通ヘルパーを使わない。
- 任意文の `POST /api/tts` は Bearer 認証、文字数・音声種類の検証を行う。トークン未設定なら無効。公開 API に認証がないこと自体を欠陥とは扱っていない。
- OAuth は OS の乱数、state、PKCE S256、ループバック待ち受けを使い、保存するトークンの権限は0600。
- 既定のサーバー待ち受けは `127.0.0.1:8080`。systemd の例には専用ユーザー、書き込み先制限、権限昇格禁止、メモリ上限がある。メモリ上限はほかのサービスを保護するが、対象プロセス自身の停止は防げない。
- 現在の追跡ファイル355件と Git 履歴527コミットを、Google API キー・GitHub トークン・AWS アクセスキー・秘密鍵のパターンで検索し、該当なし。現行ファイルでは Discord の秘密付き URL も検索した。環境変数や非追跡の認証ファイルの中身は出力していない。パターン検索は全ての秘密情報を検出する保証にはならない。
- `cargo audit --json`：265依存、既知の脆弱性0件。RustSec DB は2026-10-03更新の取得結果。`ttf-parser 0.25.1` は保守終了の警告（[RUSTSEC-2026-0192](https://rustsec.org/advisories/RUSTSEC-2026-0192.html)）、`yoke-derive 0.8.3` は yanked の警告。これらを現時点で悪用可能な脆弱性とは数えていない。
- `npm audit --json`：開発依存を含めて既知の脆弱性0件。
- Web の既存テスト217件、Rust の既存 HTTP/TTS HTTP テスト30件と履歴 API テスト6件が通過。監査用の再現テスト4件も通過（問題の挙動を確認するテスト）。最初のソケットを使う2件は実行環境の待ち受け制限で失敗し、ループバックの待ち受けを許可した再実行で通過した。

## 追加の改善候補

CI の `npm audit --omit=dev`（`.github/workflows/ci.yml:178`）は、全て `devDependencies` に入っている現在の Web ツール群を監査対象から外す。今回の全依存の監査では問題はなかったが、CI でも開発依存を含めると今後の検出漏れを減らせる。GitHub Actions の参照をコミット SHA に固定することも検討したい。

気象 XML の取得先は Atom の `href` を、`_VPWS50_` を含むことだけで選ぶ（`weather.rs:74`、`:168`）。既定の HTTPS の気象庁フィードを信用する設計では直ちに公開 SSRF にはならないが、フィードの変更・侵害まで想定するなら、リンク先とリダイレクト先の HTTPS・ホストを許可リストで制限する。

運用開始前には、本番の公開経路で TTS・履歴・WebSocket の上記制限が有効かを確認する。対処順は S-01、S-02/S-03、S-04/S-05 を推奨する。
