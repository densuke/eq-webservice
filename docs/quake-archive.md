# 地震の見直し: 履歴の再生を当時の時刻で、配信の録画を残す

2026-09-30 14:00 の与那国島近海の地震 (最大震度 3) を eq.fuga.jp の履歴で見直したとき、次の問題があった。

- 地震波が広がっている途中なのに、震度がもう出ていた。
- 時計が今の時刻のままだった。

YouTube の配信は DVR を切っているので、配信の画面は後から見返せなかった。

この文書は 3 つの仕事の仕様である。

- R1: 履歴の再生
- R2: 配信の録画のリングバッファ
- R3: 再現動画 (今回は作らず、宿題として残す)

## 1. 道具の棚卸し (2026-09-30 に確かめたこと)

- **記録 (jsonl)**
  - 本番 (e2) は `[[sinks]] type = "jsonl"`、`path = "data/events.jsonl"` で、受けた情報を全部追記している。
  - 中身は内部の `Event` を `serde_json` にしたもの。`received_at_ms` と `kind` が入っている。
  - 14:00 の地震は 14 行が全部そろっていた。
    - 緊急地震速報 (wolfx) の第 1〜11 報。どの報にも秒単位の発生時刻がある。
    - 震度速報 14:02:21、震源情報 14:05:36、各地の震度 14:06:13。
  - ファイルは約 126KB・22 行 (09-29 04:45 から)。回転や削除の仕組みは無い。
- **サーバのメモリ (Hub)**
  - 直近 200 件まで持つ。緊急地震速報は、同じ地震の最新の 1 報だけを残す (hub.rs)。
  - 過去の情報を返す API は無い。`/api/events` は直近の分だけ。
- **replay (source/replay.rs)**
  - 読めるのは上流の形式 (P2P地震情報の JSON、Wolfx の JSON) だけで、**内部の Event の jsonl は読めない**。
  - `Event` は `Deserialize` を持つので、読めるようにするのは容易。
- **web のデモ (demo.ts・demo-ui.ts)**
  - 記録を当時の時刻で再生する。各報は発表時刻に届き、`now()` がデモの時計になる。
  - 始まりは最初の報の `LEAD_MS = 5000` 前。速さは ×1 など、ボタンで選べる。
- **web の履歴 (view.ts `renderList` → main.ts `select`)**
  - 選んだ瞬間を発生時刻 (t = 0) とみなして、地震波を 3 倍速で描く (scene.ts、`REPLAY_SPEED = 3`)。
  - 震度は、そのグループの最後の情報を全部すぐ出す。
  - 時計は今の時刻のまま。
- **配信の録画**
  - ffmpeg の経路なら、`tee` と `segment` (`segment_wrap`) で圧縮し直さずにリングバッファを作れる。
  - eq-server は平時と地震の画面の切り替えを知っている (broadcast/mod.rs の `calm` の watch)。
- **native の描画**
  - 地震波と緊急地震速報は描かない (N1 の範囲外)。
  - 再現動画に地震波を入れるなら、Chrome の経路 (Web のページ) を使う。Mac では Chrome が使えるが、e2 には無い。
- **e2 のディスク**: 空き 3.8GB (使用率 87%)。

## 2. R1: 履歴の再生を当時の時刻で (web とサーバ)

### 2.1 目的

- 履歴で地震を選ぶと、その地震の **当時の時刻** で再生する。時計も当時の時刻を出す。
- 再生は、**最初の揺れ (発生時刻) の 10 秒前** から始める。
- 各報 (緊急地震速報の第 n 報、震度速報、各地の震度) は、**当時届いた時刻** に届く。
  - これで、震度は発表された時刻に出る。地震波の途中で震度が全部出ることはなくなる。
  - 地震波の起点は、今と同じ規則 (緊急地震速報があればその秒単位の発生時刻) にする。

### 2.2 サーバ: 過去の報を返す API

- `GET /api/archive?from=<ms>&to=<ms>` を足す。jsonl の記録から、`received_at_ms` がその範囲にある `Event` を時刻順の JSON 配列で返す。
- jsonl のパスは、設定の jsonl の sink と同じものを使う。
  - jsonl の sink が無ければ、この API は 404 にする (または足さない)。
  - 設定の項目を新しく増やすなら最小限にする。
- 守ること
  - `to - from` は 1 時間まで。超えたら 400。数値でなければ 400。
  - 返すのは最大 500 件。
  - 読むのは設定されたファイルだけ。利用者の入力をパスにしない。
  - 壊れた行は飛ばす (ログに 1 行出す)。
  - ファイルが大きくなっても困らないように、1 行ずつ読む。
    - `ponytail:` 全部読む。ファイルが数十 MB を超えたら、索引や日付ごとのファイルを考える。
- テスト
  - 範囲で絞れる。
  - 1 時間を超えたら 400。
  - 壊れた行を飛ばす。
  - sink が無いときの振る舞い。

### 2.3 web: 履歴の再生をデモの仕組みに乗せる

- 履歴の一覧で行を選んだら (`select`)、次の報を集める。
  - `GET /api/archive` で、その地震の発生時刻の 60 秒前から 15 分後までの報を取る。
  - 取れなければ、メモリの store にある分 (今と同じ) を使う。
- 集めた報から、同じ地震の報だけを残す。判定は `priority.ts` の同じ地震の判定を使う。
- 残した報を、デモの再生 (`makePlan`・`runScenario` 相当) で再生する。
  - 始まりは、発生時刻 (緊急地震速報があればその秒単位の発生時刻) の **10 秒前**。
  - デモの `LEAD_MS` とは別の値にするか、引数で渡す。**デモの振る舞いは変えない。**
  - 速さは ×1 から始め、デモと同じ速さのボタンを使えるようにする。
  - 画面の表示は「リプレイ中」とわかるものを残す。今のデモの表示と同じでよい。
  - 終わったら、または別の行を選んだら、ライブの表示に戻る。
  - 再生の最中に本物の情報が届いたら、どうなるかを確かめる。今のデモの振る舞いに合わせる。
- 今の「3 倍速で波だけ描き直す」再生 (`REPLAY_SPEED`) は、この再生に置き換える。使われなくなるコードは消す。
- テスト (vitest)
  - 報の集め方: 同じ地震だけ残す。
  - 始まりの時刻 = 発生時刻 − 10 秒 (緊急地震速報の秒単位の発生時刻を優先)。
  - archive が取れないときに store を使う。

### 2.4 やらないこと (今回)

- 地震波に合わせて震度を 1 地点ずつ出す演出。
  - 当時の時刻で再生すれば、震度は発表の時刻 (多くは波が通り過ぎたあと) に出るので、まず様子を見る。
- native の配信の描画の変更。

### 2.5 R1.1: 何も起きない時間を詰める (v0.18.2)

v0.18.0 を本番で使ってみて、次のことがわかった。

- 緊急地震速報の出なかった地震 (震度 3〜4 の多く) を再生すると、1〜2 分何も出ない。
- その後、震度速報で震度だけが出て、約 1 分後に震源の情報で ✕ が出る。

例として、2026-09-29 04:45 の茨城県南部 (最大震度 4) の報の流れは次のとおり。

- 震度速報 04:46:43 (震源なし)
- 震源の情報 04:47:52
- 各地の震度 04:49:17

地震情報の発生時刻は分単位 (04:45:00) なので、再生は 04:44:50 から始まる。当時の順番どおりではあるが、間延びする。

直すこと (web の history.ts と、再生の時計の進め方):

1. **始まりの時刻**
   - 緊急地震速報があれば、今のまま (その秒単位の発生時刻の 10 秒前)。
   - 緊急地震速報が無ければ、**最初の報が届いた時刻 (`received_at_ms`) の 10 秒前** から始める。
2. **間を詰める**
   - 履歴の再生の最中、次の報まで 20 秒 (`HISTORY_MAX_GAP_MS`) を超えて何も届かないときは、再生の時計を「次の報の 5 秒前」まで飛ばす (早送り)。
   - 飛ばしている間、または飛ばした直後の数秒、画面に「早送り」とわかる表示を出す。表示は時計の近く。文言は任せる。
   - 時計は飛ばした先の当時の時刻を出す (時刻の整合は保つ)。
   - **デモの再生は今のまま** (詰めない)。履歴の再生だけに効かせる。
   - 位置のつまみ (シークバー) や速さのボタンとの整合は、担当が決めてよい。例: つまみは詰めた後の長さで出す。
3. 地震波の起点は今の規則のまま (緊急地震速報の秒単位の発生時刻。無ければ地震情報の分単位の発生時刻)。
   - 震源が後から届いたときの地震波の描き直しは、今回はやらない (予想震度の札と一緒に後で考える)。

テスト (node --test、既存の history.test.ts に足す):

- 緊急地震速報が無いときの始まり = 最初の報の received_at_ms − 10 秒。
- 緊急地震速報があるときは、今と同じ。
- 間を詰める計算 (純粋な関数にする): 報の時刻の並びから、飛ばす区間 (どこからどこまで) が正しく出ること。
  - 20 秒ちょうどは飛ばさない、20 秒を超えたら飛ばす。
- デモの計画 (`makePlan`) の既存のテストが変わらず通ること。

確かめ方 (Mac):

- replay で緊急地震速報の無い記録と、ある記録 (samples/scenarios/noto2024.jsonl) を jsonl の sink に書かせ、履歴から選ぶ。
- 無い記録では、始まってすぐ (10 秒ほどで) 最初の報が出ること、間が詰まり「早送り」が出ること。
- noto2024 では、今と同じく発生の 10 秒前から始まること。
- 緊急地震速報の無い記録は、`samples/` にあるものを使う。無ければ、上の 09-29 04:45 の流れを模した短い記録を一時ファイルで作ってよい (コミットしない)。

### 2.6 R1.2: 震源と予想震度の見せ方 (v0.18.3)

v0.18.2 を本番で使ってみて、次の 2 点がわかった。

- **震源が震度より後に出る**
  - 2026-09-29 04:45 の茨城県南部 (緊急地震速報なし) を再生すると、震度速報で震度が出たあと、約 1 分後の震源の情報で初めて ✕ が出る。
  - 気象庁の発表の順番 (震度速報 → 震源 → 各地の震度) どおりではある。ただ、再生では結末がわかっているので、揺れの広がりから見せたい。
- **緊急地震速報の予報では、地図に何も出ない**
  - 2026-09-30 14:00 与那国島近海の第 1〜11 報は全部予報だった。地域ごとの予想 (`areas`) も県ごとの予想 (`pref_max`) も空で、塗るものが無い。
  - 震源 (M6.2、深さ 10km) と最大予想震度 (2 → 3) はある。一覧と詳細には「予測最大震度3」と出ているが、地図の上では手がかりが無い。

直すこと (web):

1. **再生では、後の報の震源を先に出す** (履歴の再生だけ。ライブとデモは変えない)
   - 履歴の再生を始めるとき、集めた報 (`gatherEvents` の結果) から、その地震の震源 (緯度・経度・深さ・規模) を探す。
     - 優先順位は、各地の震度 (`detail_scale`) → 震源の情報 (`destination`) → 緊急地震速報の最終報。
   - 見つかったら、再生の始まりから地図にその震源の印を出す。
     - 見た目で「後から判明した震源」とわかるようにする (薄い色、点線の ✕ など)。
     - 本物の震源の情報が届いたら、ふつうの ✕ に置き換える。
   - 地震波の同心円も、発生時刻からその震源を中心に描く。
     - 発生時刻は、緊急地震速報の秒単位の発生時刻を優先する。無ければ地震情報の分単位の発生時刻。
     - 分単位のときは、起点が最大 59 秒ずれる。この限界はコメントに残す。
   - 震度 (塗り・点・一覧) は、今どおり発表された時刻に出す。
2. **震源が後から届いたときの地震波** (ライブと再生の両方)
   - 震源のない報 (震度速報) で始まった地震に、あとから震源の情報が届いたら、その時点で地震波の描画を始める。今もそうなっているかをまず確かめる。
   - 発生から `WAVE_MAX_SEC` 以内なら、発生時刻を起点にしたその時点の半径から描く。届いたときに波がどこまで進んでいたかがわかる。
   - 今の振る舞いで既に満たしているなら、変えずにテストだけ足す。
3. **緊急地震速報の予報でも、地図に札を出す** (ライブ・デモ・再生のすべて)
   - 地域ごとの予想が空の緊急地震速報では、震源の印の近くに「予想 最大震度3」のような札を出す。
     - 地域の予想があるときは、今の破線の塗りのままでよい。そのときも札を出すかは担当が決めてよい。
   - 札の文言は、今の一覧・詳細の「予測最大震度」とそろえるか「予想 最大震度」にするか、担当が決めて統一する。
   - 続報で最大予想震度が変われば、札も変える。取り消し (`cancelled`) なら消す。
   - まず今の画面で、予報の緊急地震速報の震源の ✕ が地図に出ているかを確かめる。出ていなければ出す。
4. native の配信の描画は変えない (緊急地震速報と地震波を描かない作りのまま)。

テスト (node --test):

- 後の報から震源を探す関数 (優先順位、見つからないとき)。
- 予報の札の文言 (最大予想震度から、取り消し、地域の予想があるとき)。
- 地震波の起点の選び方 (緊急地震速報の秒単位 → 地震情報の分単位)。

確かめ方 (Mac、組み込みのブラウザ):

- 09-29 04:45 茨城県南部を模した記録 (緊急地震速報なし) と、09-30 14:00 与那国島近海の記録 (予報 11 報 + 地震情報 3 報) を jsonl の sink に書かせ、履歴から選ぶ。
  - 本番の `https://eq.fuga.jp/api/archive?from=1790744400000&to=1790745300000` で 14:00 の 14 報が取れる。読むだけ。
- 確かめること
  - 茨城では、始まりから薄い震源の印と地震波が出る。震度は発表の時刻に出て、震源の情報で ✕ がふつうの表示になる。
  - 与那国では、予報の間、震源の印と「予想 最大震度2 → 3」の札が出る。
  - noto2024 (samples) では、警報の地域の予想の塗りが今どおり出る。
- スクリーンショットか、読み取った文字を報告に書く。

### 2.7 R1.3: 履歴の再生の音 (v0.18.4)

v0.18.3 を本番で使った利用者の要望。

- 履歴の再生で、揺れの始まり (地震波が出る瞬間) に音を鳴らしたい。
- 地震波が広がっている間の 2 秒ごとの刻みの音 (`play("pip")`) を、履歴の再生でも鳴らしたい。

どちらも、音をオンにしているとき (`soundEnabled()`) だけでよい。

今の作り (web/src/main.ts の `tick`):

- 刻みの音は `waving && !sc.replay && (app.demo?.clock.speed ?? 1) <= 1` のときだけ鳴る。
- 警戒音は `onEvents` で報が届いたときに鳴る (`live` の条件あり)。
- 履歴の再生で刻みの音が鳴らない理由を、まず確かめる (`sc.replay` か、`live` か、別の条件か)。

直すこと (web、**履歴の再生だけ**。ライブとデモの鳴り方は変えない):

1. **揺れの始まりの音**
   - 履歴の再生で、再生の時計が発生時刻を過ぎた瞬間 (地震波が出始めた瞬間) に 1 回鳴らす。
     - 発生時刻は R1.2 の `hindsightOf` と同じ規則で決める (緊急地震速報の秒単位を優先、無ければ地震情報の分単位)。
   - 音は既存の `play` の種類から選ぶ。新しい音を足すなら、sound.ts の書き方に合わせて短いものにする。
     - 震度 (のちに判明する最大震度) で `alertLevel` 相当の強さを選べるなら、それでよい。選んだ理由を PR に書く。
   - 位置のつまみで発生時刻より後に飛んだときや、早送り (2.5) で飛んだときは鳴らさない。
     - 1 回の再生で 1 回だけ鳴らす。
2. **刻みの音**
   - 履歴の再生でも、地震波が広がっている間 (`waving`) は 2 秒ごとに鳴らす。条件は今のライブと同じで、速さ ×1 以下のときだけ。
   - 早送りの最中は鳴らさない。
3. 再生の最中に届いた報の警戒音 (R1 の残課題の「再生中の警戒音」) は、今の振る舞いのままでよい。
   - 1 で鳴らす音と同じ瞬間に重なる場合は、1 回にまとめる。

テスト (node --test): 鳴らすかどうかの判定を純粋な関数にしてテストする。

- 発生時刻をまたいだときだけ真。
- 飛んだときは偽。
- 刻みは速さ ×1 以下で `waving` のときだけ。

確かめ方 (Mac、組み込みのブラウザ):

- 本番の `/api/archive` から茨城 (09-29 04:45) と与那国 (09-30 14:00) の記録を取り (読むだけ)、履歴から再生する。
- 音は耳で聞けないので、`play` の呼び出しを一時的に記録して、鳴った時刻と種類を確かめる。記録の仕組みはコミットしない。

## 3. R2: 配信の録画のリングバッファと、地震のときの切り出し (e2、ffmpeg の経路)

### 3.1 目的

- 配信した画面を直近 15 分ぶん、1 分ごとのファイルで持ち続ける (リングバッファ)。
- 地震の画面に切り替わったら、その 5 分前から 10 分後までを 1 本の動画にして残す。
- YouTube への配信を邪魔しない。**録画が失敗しても配信は止めない。**

### 3.2 作り

- **リングバッファは ffmpeg に任せる** (2026-09-30 の配信の不具合で、3.6 章のとおり tee をやめ、eq-server が書く形にした)。eq-server の broadcast.toml の `output` に `tee` を書けば済むか、まず試す。
  ```
  output = ["-progress", "…/progress.txt", "-f", "tee", "-map", "0:v", "-map", "1:a",
    "[f=flv:onfail=abort]rtmps://…|[f=segment:segment_time=60:segment_wrap=15:reset_timestamps=1:onfail=ignore]/…/ring/%02d.ts"]
  ```
  - `-map` の番号や、音の入力の有無 (無音の lavfi など) は今の ffmpeg の引数に合わせて確かめる。
  - 設定だけで済むなら、コードは足さない。済まないときだけ、最小限の組み立てを足す。
  - README (または deploy/ の例) に書き方を載せる。
- **切り出しは eq-server の broadcast に足す**。設定の例:
  ```toml
  [record]
  ring_dir = "ring"        # tee の segment が書くディレクトリ
  archive_dir = "archive"
  before_min = 5
  after_min = 10
  keep = 20                # 残す本数 (古いものから消す)
  min_free_mb = 500        # ディスクの空きがこれ未満なら切り出さない (警告だけ)
  ```
  - 平時 → 地震の画面に切り替わったとき (`calm` が false になったとき) に、切り出しを予約する。
  - `after_min` 分たったら、ring_dir の `.ts` のうち、更新時刻がその範囲にかかるものを時刻順に並べる。
    それを `ffmpeg -f concat -c copy` で `archive_dir/YYYYMMDD-HHMMSS.ts` (または .mp4) にする。
    - 圧縮し直さない。子のプロセスは nice にする。
  - 予約の間にまた地震の画面になったら、予約を延ばして 1 本にまとめる (同じ地震の続きを別の動画にしない)。
  - 本数が `keep` を超えたら、古いものから消す。消すのは archive_dir の中の、自分が作った名前の形式のファイルだけ。
  - 切り出しの失敗はログに出すだけで、配信は続ける。
  - `[record]` が無ければ、何もしない (今と同じ)。
- builtin の経路と Chrome の経路は対象外。`[record]` があれば、起動時に警告だけ出す。

### 3.3 確かめ方 (Mac。YouTube には送らない)

- `tools/broadcast_load.py` か手で、replay (noto2024、speed 4) を立てる。
- `output` の tee の先を、YouTube ではなく手元の `.flv` ファイルと ring にする。
- 確かめること
  - ring に 1 分ごとのファイルが 15 個で回ること。
  - 地震の画面に切り替わってから `after_min` 後に、archive に 1 本できること。
    - 確かめる間は `after_min = 1`・`before_min = 1` にしてよい。
  - archive の動画が ffprobe で読めて、長さが期待どおりなこと。
  - ring のディレクトリを消すなどして、tee の片側を失敗させても、flv 側は止まらないこと (`onfail=ignore`)。
- CPU・メモリは、tee なしと比べて大きく増えないこと。数値を PR に書く。

### 3.4 テスト (cargo test)

- 切り出す ring のファイルの選び方 (更新時刻と範囲)。
- 予約の延長 (続けて地震の画面になったら 1 本にまとめる)。
- `keep` を超えたら古いものから消す。消す対象を自分の作った名前だけに限る。
- ディスクの空きが足りないときに切り出さない (空きの取得は関数で差し替えられるようにする)。

### 3.5 R2.1: 切り出す地震を震度で絞る (v0.19.1)

2026-09-30 18:49 のトカラ列島近海 (M2.7、最大震度 1) でも 1 本切り出された (15 分 26 秒、26MB)。
小さな地震で `keep` の枠が埋まらないよう、切り出す地震を最大震度で絞る。

- `[record]` に `min_scale` を足す (震度を 10 倍した整数。P2P地震情報の scale と同じ。例: 30 = 震度 3)。
  - 省略時は 0 で、今と同じく全部切り出す。
  - e2 では 30 にする。
- 判断は **切り出すとき** (予約の終わり) に行う。
  - 予約の範囲 (地震の画面に切り替わってから切り出すまで) に表示した地震のうち、最大震度が `min_scale` 以上のものがあれば切り出す。
  - 無ければ切り出さず、ログに 1 行出す (例: 「最大震度 1 のため切り出しません」)。
  - 地震の画面に切り替わった時点では、震度はまだわからない (震度速報は 1〜2 分後) ので、切り替わりでは判断しない。
- 緊急地震速報の **警報** を表示した場合は、震度にかかわらず切り出す。
  - v0.19.0 以降、native は緊急地震速報も表示する。
  - 予報は震度で判断する。予報の予測最大震度は数えず、観測の震度だけで判断する。
- 震度を record に渡す方法は担当が決めてよい (例: native から `watch` で「表示中の地震の最大震度・警報か」を渡す)。
  - 表示の判断は今までどおり native の model 側に置く。
- テスト
  - 範囲内の最大震度が `min_scale` 未満なら切り出さない。以上なら切り出す。
  - 警報なら切り出す。
  - `min_scale` を省略したら今と同じ。

### 3.6 R2.2: 録画を tee から切り離す (v0.19.x)

2026-09-30 20:08〜20:41、出力を tee (flv → YouTube と segment → ring) にしていた間に、YouTube の視聴ページが 20:29:14 で止まった。

- そのときの e2 の状態
  - e2 の ffmpeg は送り続けていた (speed 1x、コマは進み、YouTube との TCP も確立、送り残し 0)。
  - ring の録画には正しい画面 (時計が進んでいる) が入っていた。
- 20:41 に flv の直送へ戻すと、YouTube はまた映った。
- 原因は特定できていない。tee と YouTube の相性か、偶然の YouTube 側の詰まりかは、わからない。
- 16:14〜20:08 も tee だったが、その間に YouTube で見て確かめたのは切り替え直後の 1 回だけ。

方針: **YouTube への送り出しを、実績のある形 (ffmpeg の flv 直送) のまま変えずに、録画を別にする。**

- 案 A (勧める): 圧縮する ffmpeg は 1 つのまま、出力を **mpegts で標準出力 (pipe)** にする。eq-server がそれを読んで、次の 2 か所に流す。
  1. 送り出し用の ffmpeg (`-f mpegts -i pipe: -c copy -f flv rtmps://…`)。圧縮し直さないので軽い。
  2. ring のファイル。eq-server が 1 分ごとに `ring/%02d.ts` を書き、20 個で回す。
  - 録画の書き込みが失敗・遅れても、送り出しは止めない。ring への書き込みは別のタスクにして、詰まったら捨てる。
  - 送り出し用の ffmpeg が終わったら、今と同じく配信のやり直し (5 秒後に再接続) にする。
  - YouTube へ届く中身は「x264 → flv」で、今の直送と同じ。時刻は mpegts を経由するが、`-c copy` なのでそのまま。
- 案 B: 録画用にもう 1 つ ffmpeg を立てて、同じ rawvideo をもう一度圧縮する。CPU が約 2 倍になるので、e2 には向かない。比べるだけでよい。
- どちらでも、`[record]` の設定 (ring_dir・archive_dir・before_min・after_min・keep・min_free_mb・min_scale) と切り出しの作りは変えない。
- `output` に tee を書かなくても録画できるようにする (README と例を直す)。tee の例は消す。
- 確かめ方 (Mac)
  - 手元の RTMP の受け側 (`ffmpeg -listen 1 -i rtmp://127.0.0.1:19350/live/test -c copy recv.flv`) に **2 時間以上** 送る。
  - recv.flv が最後まで読めて、時刻が飛ばないこと。
  - ring が回り、切り出し (`before_min = 1`・`after_min = 1`、replay の noto2024) ができること。
  - ring のディレクトリを消しても送り出しが止まらないこと。
  - CPU とメモリを、今の直送 (録画なし) と比べる。増えるのは copy の ffmpeg 1 つ分 (目安 CPU 1% 未満、メモリ 20MB 前後) に収まること。
- テスト: ring の書き分け (1 分ごと、20 個で回る)、書き込みが詰まったときに送り出しを止めないこと。

### 3.8 R2.3: 送り出しの時刻の乱れを直す (R2.2 の手直し)

2026-10-01 06:23 に e2 へ v0.19.5 (R2.2) を入れたところ、次のことが起きた。

- YouTube の健全性が `good` から `ok` に下がった。
- 06:37 に受け口が inactive になり、枠が自動終了した。
- 送り出し用の ffmpeg (`-f mpegts -i pipe:0 -c copy -f flv rtmps://…`) が、`timestamp discontinuity (stream id=256): 20000000, new offset= -20000000` などを何度も出して、時刻を付け直していた。
  - 平時は 2fps で、圧縮する ffmpeg は `-use_wallclock_as_timestamps 1` の時刻を付ける。mpegts を読む側は、既定で 10 秒を超える跳び (`dts_delta_threshold`) を「途切れ」とみなす。
  - 付け直した時刻が YouTube の受け口を乱したと見られる。
- Mac の 2 時間の試験 (受け手は手元の `ffmpeg -listen 1`) では出なかった。受け手が時刻に甘いため。

直すこと:

1. まず手元で再現する。v0.19.5 の作りで、平時 (2fps) と地震の画面 (5fps) を含む流れを 30 分ほど流し、送り出し側の `timestamp discontinuity` を数える。
2. 送り出し用の ffmpeg が時刻を付け直さないようにする。候補は次のとおりで、どれが効くかを試して選ぶ。
   - `-copyts`、`-dts_delta_threshold` を大きくする、`-fflags +igndts` など。
   - 圧縮する ffmpeg の mpegts の出力の設定 (`-mpegts_copyts 1`、`-muxdelay 0` など)。
   - 送り出しに渡す前に eq-server 側で何かする。
3. **確かめ方は、手元の受け手が甘いことを前提にする。** 次の 3 つで、flv の時刻が壊れていないことを数値で示す。
   - 受け取った flv の映像と音のパケットの時刻 (ffprobe の pts・dts) が単調に増えること。
   - 実時間 (壁時計) との差が 1 秒以内にとどまること。
   - `timestamp discontinuity` が 0 回であること。
   - 同じ条件で、今の直送 (録画なし) の flv と並べて、時刻の進み方が同じであることを示す。
4. YouTube での最終確認は、利用者が戻ってから非公開のテスト枠で行う (コーディネーター)。担当は YouTube には送らない。

結果 (手元の Mac、ffmpeg 9.0.2。送り先は手元の `ffmpeg -listen 1`):

- 原因: 圧縮する ffmpeg は映像の時刻を壁時計で付け、音は無音の入力 (`-re`) の標本数で付ける。
  送り出しが詰まる (受け口への通信が止まる) と、圧縮する側が止まって映像の時刻に詰まった秒数の跳びができる。
  e2 の `20000000` (20 秒) はこれ。送り出し用の ffmpeg は、10 秒を超える跳びを「時刻の途切れ」とみなして全部の時刻を付け直し、音と映像が乱れる。
  - 平時 2fps や地震 5fps の入れ替わりだけでは出ない (平時 30 分・地震 30 分・入れ替わり 10 分で 0 回)。詰まりが要る。
  - 再現: 送り出し用の ffmpeg を 25 秒 SIGSTOP すると、直す前は `timestamp discontinuity` が 12〜13 回出て、受け取った flv の映像は 46 秒で途絶える。
- 直し方: 送り出し用の ffmpeg の入力に `-copyts -start_at_zero` を付ける (時刻をそのまま通し、0 から始める)。
  `-dts_delta_threshold` を大きくしても同じ結果になるが、`-copyts` は途切れの補正そのものを止めるので、こちらにした。
  圧縮する側の `-mpegts_copyts 1 -muxdelay 0` では直らなかった (途切れは 7 回)。
- 残る課題: 詰まりのあと、音 (`-re` は遅れを 1.05 倍で取り戻す) より映像の時刻が進んだままになり、映像が数秒おきのまとまりでしか出なくなる。
  これは直送でも同じで、時刻の付け直しとは別の問題。
