# 地震の見直し: 履歴の再生を当時の時刻で、配信の録画を残す

2026-09-30 14:00 の与那国島近海の地震 (最大震度 3) を eq.fuga.jp の履歴で見直したとき、次の問題があった。

- 地震波が広がっている途中なのに、震度がもう出ていた。
- 時計が今の時刻のままだった。

YouTube の配信は DVR を切っているので、配信の画面は後から見返せなかった。

この文書は 3 つの仕事の仕様である。

- R1: 履歴の再生
- R2: 配信の録画のリングバッファ
- R3: 再現動画 (今回は作らず、宿題として残す)

## 1. 道具の棚卸し (2026-09-30 に確かめたこと)

- **記録 (jsonl)**
  - 本番 (e2) は `[[sinks]] type = "jsonl"`、`path = "data/events.jsonl"` で、受けた情報を全部追記している。
  - 中身は内部の `Event` を `serde_json` にしたもの。`received_at_ms` と `kind` が入っている。
  - 14:00 の地震は 14 行が全部そろっていた。
    - 緊急地震速報 (wolfx) の第 1〜11 報。どの報にも秒単位の発生時刻がある。
    - 震度速報 14:02:21、震源情報 14:05:36、各地の震度 14:06:13。
  - ファイルは約 126KB・22 行 (09-29 04:45 から)。回転や削除の仕組みは無い。
- **サーバのメモリ (Hub)**
  - 直近 200 件まで持つ。緊急地震速報は、同じ地震の最新の 1 報だけを残す (hub.rs)。
  - 過去の情報を返す API は無い。`/api/events` は直近の分だけ。
- **replay (source/replay.rs)**
  - 読めるのは上流の形式 (P2P地震情報の JSON、Wolfx の JSON) だけで、**内部の Event の jsonl は読めない**。
  - `Event` は `Deserialize` を持つので、読めるようにするのは容易。
- **web のデモ (demo.ts・demo-ui.ts)**
  - 記録を当時の時刻で再生する。各報は発表時刻に届き、`now()` がデモの時計になる。
  - 始まりは最初の報の `LEAD_MS = 5000` 前。速さは ×1 など、ボタンで選べる。
- **web の履歴 (view.ts `renderList` → main.ts `select`)**
  - 選んだ瞬間を発生時刻 (t = 0) とみなして、地震波を 3 倍速で描く (scene.ts、`REPLAY_SPEED = 3`)。
  - 震度は、そのグループの最後の情報を全部すぐ出す。
  - 時計は今の時刻のまま。
- **配信の録画**
  - ffmpeg の経路なら、`tee` と `segment` (`segment_wrap`) で圧縮し直さずにリングバッファを作れる。
  - eq-server は平時と地震の画面の切り替えを知っている (broadcast/mod.rs の `calm` の watch)。
- **native の描画**
  - 地震波と緊急地震速報は描かない (N1 の範囲外)。
  - 再現動画に地震波を入れるなら、Chrome の経路 (Web のページ) を使う。Mac では Chrome が使えるが、e2 には無い。
- **e2 のディスク**: 空き 3.8GB (使用率 87%)。

## 2. R1: 履歴の再生を当時の時刻で (web とサーバ)

### 2.1 目的

- 履歴で地震を選ぶと、その地震の **当時の時刻** で再生する。時計も当時の時刻を出す。
- 再生は、**最初の揺れ (発生時刻) の 10 秒前** から始める。
- 各報 (緊急地震速報の第 n 報、震度速報、各地の震度) は、**当時届いた時刻** に届く。
  - これで、震度は発表された時刻に出る。地震波の途中で震度が全部出ることはなくなる。
  - 地震波の起点は、今と同じ規則 (緊急地震速報があればその秒単位の発生時刻) にする。

### 2.2 サーバ: 過去の報を返す API

- `GET /api/archive?from=<ms>&to=<ms>` を足す。jsonl の記録から、`received_at_ms` がその範囲にある `Event` を時刻順の JSON 配列で返す。
- jsonl のパスは、設定の jsonl の sink と同じものを使う。
  - jsonl の sink が無ければ、この API は 404 にする (または足さない)。
  - 設定の項目を新しく増やすなら最小限にする。
- 守ること
  - `to - from` は 1 時間まで。超えたら 400。数値でなければ 400。
  - 返すのは最大 500 件。
  - 読むのは設定されたファイルだけ。利用者の入力をパスにしない。
  - 壊れた行は飛ばす (ログに 1 行出す)。
  - ファイルが大きくなっても困らないように、1 行ずつ読む。
    - `ponytail:` 全部読む。ファイルが数十 MB を超えたら、索引や日付ごとのファイルを考える。
- テスト
  - 範囲で絞れる。
  - 1 時間を超えたら 400。
  - 壊れた行を飛ばす。
  - sink が無いときの振る舞い。

### 2.3 web: 履歴の再生をデモの仕組みに乗せる

- 履歴の一覧で行を選んだら (`select`)、次の報を集める。
  - `GET /api/archive` で、その地震の発生時刻の 60 秒前から 15 分後までの報を取る。
  - 取れなければ、メモリの store にある分 (今と同じ) を使う。
- 集めた報から、同じ地震の報だけを残す。判定は `priority.ts` の同じ地震の判定を使う。
- 残した報を、デモの再生 (`makePlan`・`runScenario` 相当) で再生する。
  - 始まりは、発生時刻 (緊急地震速報があればその秒単位の発生時刻) の **10 秒前**。
  - デモの `LEAD_MS` とは別の値にするか、引数で渡す。**デモの振る舞いは変えない。**
  - 速さは ×1 から始め、デモと同じ速さのボタンを使えるようにする。
  - 画面の表示は「リプレイ中」とわかるものを残す。今のデモの表示と同じでよい。
  - 終わったら、または別の行を選んだら、ライブの表示に戻る。
  - 再生の最中に本物の情報が届いたら、どうなるかを確かめる。今のデモの振る舞いに合わせる。
- 今の「3 倍速で波だけ描き直す」再生 (`REPLAY_SPEED`) は、この再生に置き換える。使われなくなるコードは消す。
- テスト (vitest)
  - 報の集め方: 同じ地震だけ残す。
  - 始まりの時刻 = 発生時刻 − 10 秒 (緊急地震速報の秒単位の発生時刻を優先)。
  - archive が取れないときに store を使う。

### 2.4 やらないこと (今回)

- 地震波に合わせて震度を 1 地点ずつ出す演出。
  - 当時の時刻で再生すれば、震度は発表の時刻 (多くは波が通り過ぎたあと) に出るので、まず様子を見る。
- native の配信の描画の変更。

### 2.5 R1.1: 何も起きない時間を詰める (v0.18.2)

v0.18.0 を本番で使ってみて、次のことがわかった。

- 緊急地震速報の出なかった地震 (震度 3〜4 の多く) を再生すると、1〜2 分何も出ない。
- その後、震度速報で震度だけが出て、約 1 分後に震源の情報で ✕ が出る。

例として、2026-09-29 04:45 の茨城県南部 (最大震度 4) の報の流れは次のとおり。

- 震度速報 04:46:43 (震源なし)
- 震源の情報 04:47:52
- 各地の震度 04:49:17

地震情報の発生時刻は分単位 (04:45:00) なので、再生は 04:44:50 から始まる。当時の順番どおりではあるが、間延びする。

直すこと (web の history.ts と、再生の時計の進め方):

1. **始まりの時刻**
   - 緊急地震速報があれば、今のまま (その秒単位の発生時刻の 10 秒前)。
   - 緊急地震速報が無ければ、**最初の報が届いた時刻 (`received_at_ms`) の 10 秒前** から始める。
2. **間を詰める**
   - 履歴の再生の最中、次の報まで 20 秒 (`HISTORY_MAX_GAP_MS`) を超えて何も届かないときは、再生の時計を「次の報の 5 秒前」まで飛ばす (早送り)。
   - 飛ばしている間、または飛ばした直後の数秒、画面に「早送り」とわかる表示を出す。表示は時計の近く。文言は任せる。
   - 時計は飛ばした先の当時の時刻を出す (時刻の整合は保つ)。
   - **デモの再生は今のまま** (詰めない)。履歴の再生だけに効かせる。
   - 位置のつまみ (シークバー) や速さのボタンとの整合は、担当が決めてよい。例: つまみは詰めた後の長さで出す。
3. 地震波の起点は今の規則のまま (緊急地震速報の秒単位の発生時刻。無ければ地震情報の分単位の発生時刻)。
   - 震源が後から届いたときの地震波の描き直しは、今回はやらない (予想震度の札と一緒に後で考える)。

テスト (node --test、既存の history.test.ts に足す):

- 緊急地震速報が無いときの始まり = 最初の報の received_at_ms − 10 秒。
- 緊急地震速報があるときは、今と同じ。
- 間を詰める計算 (純粋な関数にする): 報の時刻の並びから、飛ばす区間 (どこからどこまで) が正しく出ること。
  - 20 秒ちょうどは飛ばさない、20 秒を超えたら飛ばす。
- デモの計画 (`makePlan`) の既存のテストが変わらず通ること。

確かめ方 (Mac):

- replay で緊急地震速報の無い記録と、ある記録 (samples/scenarios/noto2024.jsonl) を jsonl の sink に書かせ、履歴から選ぶ。
- 無い記録では、始まってすぐ (10 秒ほどで) 最初の報が出ること、間が詰まり「早送り」が出ること。
- noto2024 では、今と同じく発生の 10 秒前から始まること。
- 緊急地震速報の無い記録は、`samples/` にあるものを使う。無ければ、上の 09-29 04:45 の流れを模した短い記録を一時ファイルで作ってよい (コミットしない)。

## 3. R2: 配信の録画のリングバッファと、地震のときの切り出し (e2、ffmpeg の経路)

### 3.1 目的

- 配信した画面を直近 15 分ぶん、1 分ごとのファイルで持ち続ける (リングバッファ)。
- 地震の画面に切り替わったら、その 5 分前から 10 分後までを 1 本の動画にして残す。
- YouTube への配信を邪魔しない。**録画が失敗しても配信は止めない。**

### 3.2 作り

- **リングバッファは ffmpeg に任せる**。eq-server の broadcast.toml の `output` に `tee` を書けば済むか、まず試す。
  ```
  output = ["-progress", "…/progress.txt", "-f", "tee", "-map", "0:v", "-map", "1:a",
    "[f=flv:onfail=abort]rtmps://…|[f=segment:segment_time=60:segment_wrap=15:reset_timestamps=1:onfail=ignore]/…/ring/%02d.ts"]
  ```
  - `-map` の番号や、音の入力の有無 (無音の lavfi など) は今の ffmpeg の引数に合わせて確かめる。
  - 設定だけで済むなら、コードは足さない。済まないときだけ、最小限の組み立てを足す。
  - README (または deploy/ の例) に書き方を載せる。
- **切り出しは eq-server の broadcast に足す**。設定の例:
  ```toml
  [record]
  ring_dir = "ring"        # tee の segment が書くディレクトリ
  archive_dir = "archive"
  before_min = 5
  after_min = 10
  keep = 20                # 残す本数 (古いものから消す)
  min_free_mb = 500        # ディスクの空きがこれ未満なら切り出さない (警告だけ)
  ```
  - 平時 → 地震の画面に切り替わったとき (`calm` が false になったとき) に、切り出しを予約する。
  - `after_min` 分たったら、ring_dir の `.ts` のうち、更新時刻がその範囲にかかるものを時刻順に並べる。
    それを `ffmpeg -f concat -c copy` で `archive_dir/YYYYMMDD-HHMMSS.ts` (または .mp4) にする。
    - 圧縮し直さない。子のプロセスは nice にする。
  - 予約の間にまた地震の画面になったら、予約を延ばして 1 本にまとめる (同じ地震の続きを別の動画にしない)。
  - 本数が `keep` を超えたら、古いものから消す。消すのは archive_dir の中の、自分が作った名前の形式のファイルだけ。
  - 切り出しの失敗はログに出すだけで、配信は続ける。
  - `[record]` が無ければ、何もしない (今と同じ)。
- builtin の経路と Chrome の経路は対象外。`[record]` があれば、起動時に警告だけ出す。

### 3.3 確かめ方 (Mac。YouTube には送らない)

- `tools/broadcast_load.py` か手で、replay (noto2024、speed 4) を立てる。
- `output` の tee の先を、YouTube ではなく手元の `.flv` ファイルと ring にする。
- 確かめること
  - ring に 1 分ごとのファイルが 15 個で回ること。
  - 地震の画面に切り替わってから `after_min` 後に、archive に 1 本できること。
    - 確かめる間は `after_min = 1`・`before_min = 1` にしてよい。
  - archive の動画が ffprobe で読めて、長さが期待どおりなこと。
  - ring のディレクトリを消すなどして、tee の片側を失敗させても、flv 側は止まらないこと (`onfail=ignore`)。
- CPU・メモリは、tee なしと比べて大きく増えないこと。数値を PR に書く。

### 3.4 テスト (cargo test)

- 切り出す ring のファイルの選び方 (更新時刻と範囲)。
- 予約の延長 (続けて地震の画面になったら 1 本にまとめる)。
- `keep` を超えたら古いものから消す。消す対象を自分の作った名前だけに限る。
- ディスクの空きが足りないときに切り出さない (空きの取得は関数で差し替えられるようにする)。

## 4. R3: 再現動画 (今回は作らない、宿題)

- replay が内部の Event の jsonl (と `/api/archive` の結果) を読めるようにする。
- それを使って、地震の前後を Chrome の経路 (地震波あり) で描き直し、ファイルにする。
- YouTube Data API でアップロードする (OAuth の認証が要る)。
- R1 と R2 が落ち着いてから仕様を書く。
