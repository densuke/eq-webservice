    レイアウト設計システム (案)

    試作あり: この案の「領域と比率」を、実際にコードで書いて描けるようにしたものが レイアウト定義プレビュー です。いまの PC の配置を定義で書いて描くと、実測と 1px 以内で一致します (tools/check-layout.mjs)。

    画面サイズ・デバイスごとに「どのレイアウトを基準にするか」と、部品を「どれを・どの割合で・どこに置くか」の案です。提案・ドラフト 決定事項ではなく、決める論点を絞るための叩き台です。

    基準: v0.31.0 の実測 (docs/ui-spec/measured.js)参照: JDQ・JQuake のスクリーンショット (概算)状態: ドラフト

    割合の確度: 「実測」は Chromium で測った値、「概算」は共有されたスクリーンショットからの目測 (±3% 程度) です。

    1考え方

    • 基準は「プロファイル」: デバイス名ではなく、幅・高さ・縦横比から選ぶ (4 つの案: regular / compact と、配信の 2 つの参照型)。
    • 領域 (スロット) と比率で並べ、部品は「どのスロットに入るか」と「大きさの方針 (固定 / 割合 / 内容 / 残り)」だけを持つ。px の直書きと、部品どうしの手計算をなくす (仕様書 第 7 章の C1〜C4)。
    • 共有スロット: 同じ枠に、状態で中身が入れ替わる (JDQ・JQuake の左上: 状態文 → EEW の札 → 津波のパネル)。うちの「出し入れ」より、この流儀が参照画面に近い。
    • 情報量の段階 (簡易 / 詳細) を部品の属性に。津波は JQuake 型 = 簡易 (札 + 沿岸線の色)、JDQ 型 = 詳細 (到達予想の表)。

    5決めたいこと

      答えが決まる順に、次の作業 (プロファイルごとの詳細な座標・部品の契約・移行の手順) が決まります。第 1・2 問が決まれば、残りの多くは機械的に決まります。

      6第 1 段階: いまの web を定義で再現 実装済み

      レイアウトの定義を web 本体に持ち込み、いまのページを定義どおりに並べ直す形に置き換えました。見た目は変えず、仕組みだけを置き換えるのが目的です。

      • 定義: web/src/layout.ts の LAYOUTS (regular = 幅 801 以上、compact = 800 以下)。段階 0.5 からは web/src/layout.json (下の「定義ファイル」)。部品の名前と、いまの要素の対応は web/src/layout-dom.ts の SLOTS。
      • 並べ方: 起動時と画面の大きさが変わったときに、合う定義を選び、要素を容器 (flex) と地図の隅の積み (重ね物) へ入れ直す。
      • CSS から外したもの: 重ね物の位置の手計算 (left: 246px・:has() で top: 242px・bottom: 96px など) と、本体の grid。部品の見た目 (色・大きさ・文字) はそのまま。
      • テスト: web/src/layout.test.ts (定義の選び方・大きさの変換・全部品が 1 回ずつ置かれていること)。

      • 条件: 幅 801px 以上・高さ 480px 以下 (定義の landscape)。PC とスマホ縦の見た目は変えていない (実測で ±1px 一致を確認)。

      定義ファイル (段階 0.5) 実装済み

      レイアウトの定義を、ビルドに入れるコードから外のファイル (JSON) に出しました。部品そのもの (web の app.js・Rust の native) はこれまでどおりビルドに入れ、並びだけをファイルで変えます (Rust の動的ライブラリの部品は、ABI が安定しないので採らない)。

      • 組み込みの定義: web/src/layout.json。web の app.js と eq-server の両方に入る (同じファイル)。
      • 差し替え: eq-server の設定 [layout] file = "data/layout.json"。GET /api/layout が毎回ファイルを読み直して返すので、ファイルを書き換えてブラウザを再読み込みすれば変わる (npm のビルド・Rust のビルド・サーバの再起動は要らない)。設定が無い・読めない・JSON でないときは、警告を出して組み込みの定義を返す。
      • 確かめ方: web が読み込んだ定義を確かめ (web/src/layout.ts の checkLayouts)、正しくなければブラウザのコンソールに理由を出して組み込みの定義のまま並べる (ページは止めない)。
      • テスト: 同梱の layout.json が確かめを通り、組み込みと同じであること。知らない部品・置いていない部品・2 回置いた部品・使えない大きさ・知らない容器 / 隅 / キーを見つけること。組み込みの定義で、PC・スマホ縦・横向きの 5 つの画面の大きさで main と位置が一致することを実測で確認。
      キー中身
      version1 (書式を変えたら上げる)
      layouts[]上から順に、when に最初に合うものを使う。どれにも合わなければ先頭
      name / when / scroll名前 (body[data-layout] になる) / minWidth・maxWidth・minHeight・maxHeight (px) / "page" (ページ全体がスクロール)
      root とその下の節容器 { dir, box?, size?, children, overlays? } か、部品 { slot, variant?, size?, overlays? }。box は既存の要素 (layout・side)
      sizefill・fill:2 (残りを重みで分ける)・auto (中身の大きさ)・数 + 単位 (px・%・svh・vw など)・calc()・clamp()・min()・max()
      overlays隅 (top-left・top-right・bottom-left・bottom-right・top・bottom) → { flow, items, gap?, pad?, minHeight? }。items は部品の名前・{ slot, variant }・入れ子の { flow, items }
      gap / pad / minHeight重ね物の積み (入れ子も含む) の、中身の間隔 / 内側の余白 / 最小の高さ。値は CSS の長さ (pad は 1〜4 個)。minHeight を付けた積みは、中身が全部隠れても場所を取る
      manualtrue の定義は、画面の大きさでは選ばれず、URL の ?layout=名前 でだけ選ばれる。?layout= は manual でない定義も名前で選べる。ただし定義に when があれば、それに合うときだけ (合わなければ自動の選び方に戻る)。名前の重複は誤り。manual でない定義は 1 つ以上要る
      subMap (最上位・任意)サブの地図 (trial の右上) の設定 { hold, unknownSec, fadedAlpha }。hold は上から順に、最大震度が maxScale 以下の最初の規則の sec 秒 (最後の規則だけ maxScale なし)。unknownSec は最大震度が分からないとき。fadedAlpha は保持時間を過ぎたあとの濃さ (0〜1)。既定は震度 2 以下 60 秒・4 以下 180 秒・5強以下 600 秒・それ以上 900 秒、不明 180 秒、濃さ 0.4。震度の値は 10=1, 20=2, 30=3, 40=4, 45=5弱, 50=5強, 55=6弱, 60=6強, 70=7
      note説明 (どこにでも書ける。JSON にはコメントが無いため)

      各定義は、部品 (web/src/layout-dom.ts の SLOTS) を高々 1 回ずつ置く。必須は main だけ。省いた部品と使わない容器は、body 直下の隠し置き場 (.ld-unused、hidden) へ移る (文書から外れないので、他のコードが要素を探せる)。知らないキーも誤りにする (書き間違いに気づけるように)。

      試験定義 trial (JDQ の形)

      ?layout=trial で選ぶ (manual)。JDQ の画面の形に並べる。

      • 左: 全国の地図 (main)。下の帯に時計 (clock) とお知らせ (notice) を置く。帯 (banners) の札は地図の左上に重ねる。
      • 右: サブの地図 (map-sub、右列の 40%)・詳細 (detail、auto)・緊急地震速報の常設パネル (eew-panel)・履歴・出典。デモの操作パネルは trial では高さ 25vh まで。
      • 天気の札は、地図の重ね物に入った帯の札 (trial も) を避ける。

      緊急地震速報の常設パネルは、発表中は最優先の 1 件 (震源・発生・規模・深さ・予測最大震度・報) と「ほか n 件」を出し、平時は「現在、発表はありません」と最後の発表を出す。

      サブの地図の振る舞い

      • 映すのは currentGroup の地震。履歴の選択・巡回に追従し、「警報・注意報」ボタンを押したあとも残る。
      • 描くもの: EEW の予想 → 震度速報の区域の札 → 確定の観測点の点。揺れた範囲が広くても、区域と観測点で描く。
      • 表示中の地震へ一度に寄る (動きなし)。
      • サブの地図が見えている間、左の地図は日本全体のまま (履歴で地震を選んだときだけ寄る)。P 波・S 波は日本全体の上に描く。
      • 最後の情報から保持時間 (subMap.hold) の間ははっきり出し、過ぎたら同じ絵を fadedAlpha の濃さで薄く残す。
      • 左の地図の戻り方 (priority.ts の settleMs) は別で、変えていない。

      配備の注意: eq-server の [layout] file で外部の定義ファイルを使っているときは、web と同じ版の layout.json に更新すること。古い compact の定義では、スマホ縦の余白と場所取りが消える (CSS の補いを消したため)。

      配信 (native) が同じファイルを読むために要るもの (段階 4。いまは native を変えていない): 定義の型を serde で持ち、web と同じ確かめ方をする / 部品の名前 → native の描き方の対応 / 固定の 1280×720 で選ぶ条件 (例: when: { target: "broadcast" }。web はそれを選ばない) / fill・auto・px・% を native の矩形の割り付けに直す処理 (svh・vw・clamp() は画面の大きさで計算するか、native では使えない値として扱う)。

      今後の課題は、リポジトリの docs/ui-layout-backlog.md に一覧で残しています (実機での確認・書式の拡張・縦画面の改善・2 地図・データ源の確認など)。

      第 2 段階以降の候補 (要望)

      • 縦画面 (スマホ) で地図を画面に固定し、下の情報の部分だけをスクロールさせる。定義では、いまの scroll: "page" (ページ全体がスクロール) の代わりに「情報の部分だけスクロール」を選べるようにする。
      • スクロールすると地図が一時的に小さくなり、情報の部分を縦に広く使えるようにする。定義では、地図の大きさを幅で持つ (例: いつもは 60svh、スクロール中は 30svh)。CSS のスクロール連動か、少しのスクリプトで実現できる見込み。
      • どちらも「普段の表示の移行 (第 1 段階)」が済んでから。地図の大きさが変わると、地図のカメラと天気の札の置き直しが走るので、その負荷の確認が要る。

      このページの「レイアウト定義プレビュー」の定義 (layout-def.js) は書式を試したときの下書きで、実際に使っている定義は web/src/layout.json (と eq-server の定義ファイル)。
